# 分布式一致性方案

> 状态说明：SQLite 路径已完成仓库内确定性验证；`PostgresStateStore`、SQL profile、
> RLS/分区/cron/归档已在仓库实现，但托管 PolarDB 尚未完成外部联调。本文只描述当前
> 可从代码与测试复核的能力，不把规划或数据库通用能力写成实测结论。

## 1. 当前实现：SQLite 单写事务与约束门禁

### 1.1 连接与事务

`SQLiteStateStore.connect()` 当前只设置：

```python
conn.execute("PRAGMA foreign_keys = ON")
conn.execute("PRAGMA busy_timeout = 10000")
```

状态变更在 `transaction()` 中使用：

```python
conn.execute("BEGIN IMMEDIATE")
```

这会在事务开始时获取 SQLite 写锁，使同一数据库文件上的写事务串行化。当前实现没有
设置 `PRAGMA journal_mode=WAL`；新建数据库实测仍为 SQLite 默认的
`journal_mode=delete`。仓库也没有 `row_version` 字段或
`UPDATE ... WHERE row_version = ?` 形式的乐观锁。

### 1.2 当前并发与重复写防线

| 防线 | 实现 | 作用 |
|---|---|---|
| 单写事务 | `BEGIN IMMEDIATE` | 同一 SQLite 文件上的写事务串行化 |
| 锁等待 | `busy_timeout=10000` | 短暂争用时最多等待 10 秒 |
| 请求幂等 | `idempotency_key` 主键 + 请求指纹校验 | 同键同请求安全重放，同键异请求拒绝 |
| 动作唯一性 | `approvals(action_id)`、`workorders(action_id)` 唯一索引 | 防止同一动作产生第二个审批或工单 |
| 有效冻结唯一性 | `(incident_id, batch_id)` 的 active 部分唯一索引 | 防止同事件同批次重复生效冻结 |
| 条件更新 | 状态条件 `UPDATE` + `rowcount` 检查 | 拒绝状态已变化或目标数量不一致的写入 |

这些约束能支撑当前单进程、单 SQLite 文件的确定性评测，但不等于已完成多线程、
多进程或高争用压力验证。仓库目前没有正式并发压测结果。

### 1.3 当前适用边界

| 场景 | 状态 | 说明 |
|---|---|---|
| 单节点确定性 Demo/测试 | 已验证 | 真实临时 SQLite、事务、约束与幂等路径 |
| 多读单写 | 可用但未压测 | 读写行为受 `journal_mode=delete` 与锁竞争影响 |
| 多进程高争用 | 未验证 | 需要单独设计冲突、超时和吞吐压测 |
| 多节点共享写 | 不适用 | SQLite 文件不是本项目的分布式状态后端 |

## 2. 分布式目标：PolarDB PostgreSQL

### 2.1 已实现与未验证

仓库已有 `PostgresStateStore`、核心/安全/cron/归档 SQL profile，以及 RLS、分区等
静态契约测试。仍待真实托管实例验证：

- schema bootstrap、账号权限和 tenant scope；
- 事务隔离级别下的冲突行为；
- 连接池、超时、重试和故障恢复；
- RLS、分区、cron、归档与回滚；
- 吞吐、P95/P99 延迟和容量基线。

`PostgresStateStore` 的事务路径提交成功或回滚异常，但这不自动证明托管环境的一致性、
可用性或 SLA。

### 2.2 迁移路径

```text
阶段 1：SQLite 单节点（仓库内确定性验证已完成）
    ↓ 在隔离环境初始化 PostgreSQL profile 并跑契约/回归
阶段 2：单租户灰度切换到 PostgresStateStore（当前不做未实现的双写）
    ↓ 核对权限、RLS、分区、归档、性能与回滚证据
阶段 3：托管 PolarDB 主路径（外部待验证）
```

迁移不能简化为“只改连接串”。需要明确数据迁移、切换窗口、失败回退和状态核对方案。

## 3. 评委问题回答

### Q：当前是否使用 WAL 和乐观锁？

**A：没有。** 当前 SQLite 使用默认 `journal_mode=delete`、`BEGIN IMMEDIATE` 单写事务、
唯一约束、幂等请求指纹和条件更新。仓库没有 `row_version` 乐观锁。

### Q：当前一致性机制够不够？

**A：足够支撑已验证的单节点确定性评测，但不能外推到高并发或分布式生产。**

- 同一 SQLite 文件的写事务由 `BEGIN IMMEDIATE` 串行化；
- 业务唯一约束、幂等键和条件更新阻止重复副作用与部分陈旧写；
- 目前没有多线程/多进程争用压测，也没有正式性能基准。

### Q：需要在应用层实现 Raft/Paxos 吗？

**A：当前不自行实现共识协议。** 单节点路径依赖 SQLite 事务；分布式目标路径依赖
PostgreSQL/PolarDB 事务与托管能力。未来是否需要额外共识层，取决于跨库、多主、容灾和
一致性目标，不能在托管实例未验收时预先断言。

### Q：PolarDB 会自动解决多活业务冲突吗？

**A：不能这样承诺。** `ON CONFLICT` 只执行预先定义的数据库冲突策略，不会自动理解
事件关闭、批次处置或审批等业务冲突。多活写入必须明确冲突键、胜出规则、补偿与审计，
并在真实拓扑中验证。

## 4. 总结

| 维度 | SQLite 当前实现 | PolarDB PostgreSQL 目标路径 |
|---|---|---|
| 一致性机制 | `BEGIN IMMEDIATE` + 约束/幂等/条件更新 | 数据库事务 + 业务约束，需外部联调 |
| journal mode | `delete`（新库实测） | 不适用 |
| 乐观锁 | 未实现 | 当前也不以 `row_version` 为设计前提 |
| 已验证范围 | 单节点确定性测试 | 代码与 SQL 静态契约 |
| 未验证范围 | 高争用并发与性能 | 托管实例、权限、性能、容灾和回滚 |

**核心结论**：本项目当前使用 SQLite 单写事务与数据库/业务约束组合，不是 WAL 或
`row_version` 模式。该实现适合本地评测；生产分布式能力必须以真实 PolarDB 联调与压力证据为准。
