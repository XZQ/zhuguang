# 状态一致性与恢复边界

> 复核日期：2026-09-12。本文描述仓库实现；生产吞吐、托管 PolarDB、多机容灾须在目标环境验证。

## 1. 存储层职责

IncidentService 是业务状态唯一入口。协调 Context completed 和成功 checkpoint 不能替代业务 RESOLVED/CLOSED。

| 层次 | 当前机制 | 边界 |
|---|---|---|
| 业务 SQLiteStateStore | BEGIN IMMEDIATE、10 秒 busy_timeout、唯一约束、请求指纹和条件更新 | 不强制启用 WAL，新业务库可为默认 delete；同一文件上的写事务串行化 |
| 独立 ContextBus | WAL、tenant/task 主键、expected_version、TTL、lease 和 checkpoint | 独立协调控制面，演练数据不自动导入业务 runtime |
| RuntimeContextBus | runtime_contexts 位于业务库，版本提交与领域动作共用事务 | 不能把独立 ContextBus 的 WAL 概括为所有业务库均使用 WAL |
| Incident 聚合 | case_json.version 的 CAS，核验记录与聚合原子更新 | 旧快照被拒；乐观版本不要求列名必须叫 row_version |
| 恢复容量 | SQLite 写事务或 PostgreSQL 事务 advisory lock 串行化同门店决策 | 多扫描器采用相同身份范围；目标 PostgreSQL 竞争仍需条件集成验证 |

实现：[StateStore](../src/dianxun/state/store.py)、[ContextBus](../src/dianxun/context_bus.py)、[RuntimeContextBus](../src/dianxun/runtime_context.py)、[恢复调度](../src/dianxun/recovery.py)。

## 2. 原子性、幂等和恢复

嵌套事务使用 SAVEPOINT。内部操作失败，即使异常被转换成工具错误，仍回滚该操作的业务、审计和幂等记录；外层提交失败则回滚全部变更。

同一 idempotency_key 必须对应相同请求指纹。相同动作换 key 也不能绕过 action 唯一性创建第二次副作用。审批绑定事件、动作、金额或批次；解禁还需有效且新鲜的独立核验。

Incident、Context、assignment 和 checkpoint 在版本条件提交时竞争，不能覆盖较新的状态。硬截止、等待唤醒、恢复总预算、未知回执与 Human 运维流程见[恢复手册](operations/runtime-recovery.md)。

当前同步数据库适配器将业务和回执放在短事务中。接入真实 POS/维修网络写入时，须拆成短事务记录意图、事务外稳定幂等调用、短事务回执核对。数据库回滚和关闭 socket 都不能撤销已发生的外部副作用。

## 4. PostgreSQL / PolarDB 迁移

仓库已有 PostgresStateStore 与 core/security/cron/archive SQL profile。迁移须核对版本、schema bootstrap、权限、tenant/store RLS、索引、失败和回滚，不能描述为只换连接串。

先在隔离实例跑集成测试，再单租户灰度、对账及备份恢复演练。应用层未自行实现 Raft/Paxos，也不承诺跨库多主自动合并。ON CONFLICT 只执行指定冲突策略，不会自行理解批次处置或事件关闭。

操作入口：[Worker 接口](operations/worker-runtime.md)、[SLO 与演练](operations/SLO与恢复演练.md)。旧复赛答复保留在[归档](archive/2026-09-semifinals/README.md)，现行一致性口径以本页为准。
