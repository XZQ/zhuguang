## 1. 当前方案：SQLite WAL + 乐观锁

### 1.1 SQLite WAL 模式

```python
# src/dianxun/state/store.py
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA synchronous=FULL")
conn.execute("PRAGMA busy_timeout=10000")
conn.execute("PRAGMA foreign_keys = ON")
```

**WAL (Write-Ahead Logging) 特性**：
- 写操作并发进行，不阻塞读操作
- `BEGIN IMMEDIATE` 事务获取写锁，避免写冲突
- `busy_timeout=10000ms` 等待锁释放

### 1.2 乐观锁实现

```python
# 幂等键冲突检测
idempotent_key UNIQUE(primary key)

# 行版本约束（部分场景）
UPDATE ... WHERE row_version = expected_version
```

### 1.3 当前方案适用场景

| 场景 | 适用性 | 说明 |
|------|--------|------|
| 单节点部署 | ✅ | WAL+事务完全够用 |
| 多读单写 | ✅ | 读不阻塞，写冲突少 |
| 多写并发 | ⚠️ | 高并发时可能冲突 |

## 2. 分布式方案：PolarDB PostgreSQL

### 2.1 为什么选择 PolarDB

| 对比项 | Raft/Paxos | PolarDB MVCC |
|--------|------------|--------------|
| 实现复杂度 | 高（需要自行实现） | 低（数据库原生支持） |
| 延迟 | 取决于共识与网络 | 仍有数据库网络与事务开销，需实测 |
| 兼容性 | 需要设计应用协议 | 已有 PostgreSQL 适配器，但仍需建库、权限与 profile 配置 |
| 一致性 | 线性一致性 | 可调一致性（会话级） |

### 2.2 PolarDB 一致性保证

```python
# src/dianxun/state/postgres.py（结构摘录）
class PostgresStateStore(SQLiteStateStore):
    """PolarDB PostgreSQL backend reusing the audited repository operations."""

    backend_name = "postgresql"

    def transaction(self):
        connection = self.connect()
        try:
            yield connection
            connection.commit()
        except Exception:
            connection.rollback()
            raise
        finally:
            connection.close()
```

### 2.3 部署配置

```yaml
# 配置示意；实际部署入口见 config/project-facts.json 与 dianxun db-bootstrap

  connection_string: postgresql://user:pass@polardb-host:5432/dianxun

```

### 2.4 迁移路径

```

阶段2：单租户灰度切换到 PostgresStateStore（不做未实现的双写）

阶段3：托管 PolarDB 主路径（外部待验证）
```

## 3. 评委问题回答

### Q: 乐观锁够不够？

**A**: 在当前单节点评测场景下，SQLite WAL + 乐观锁完全够用。

- WAL 模式保证写操作不阻塞读
- `BEGIN IMMEDIATE` 事务在事务开始时获取写锁
- `busy_timeout=10000ms` 处理短暂锁等待
- 幂等键防止重复执行

### Q: 需要 Raft/Paxos 吗？

**A**：当前业务状态统一交给数据库事务和行锁处理，应用层不自行实现 Raft/Paxos；
是否需要额外共识层取决于未来跨库、多主和容灾目标，不能笼统断言为“不需要”。

- Raft/Paxos 需要在应用层实现，复杂度高
- 托管数据库降低自建数据库运维成本，但一致性、容灾和 SLA 仍需按实际规格验收
- 仓库已有 PostgreSQL 适配器，切换仍需 schema bootstrap、账号权限、RLS scope 和回归验证

### Q: 分布式场景下的一致性？

**A**：当前实现依赖 PostgreSQL 事务语义；实际可用隔离级别与只读一致性能力应以所购
PolarDB PostgreSQL 版本和官方文档为准，并在托管实例上验证。

| 级别 | 延迟 | 适用场景 |
|------|------|----------|
| READ_COMMITTED | 低 | 大多数业务场景 |
| SERIALIZABLE | 高 | 金融级一致性需求 |

## 5. 总结

| 维度 | 当前方案 | 分布式方案 |
|------|----------|------------|
| 一致性 | 事务级 | 可调（会话/全局） |
| 可用性 | 单节点 | 多可用区 |
| 延迟 | 未形成正式基准 | 未形成托管实例基准 |
| 复杂度 | 低 | 中（数据库托管） |
| 成本 | 低（SQLite） | 中（PolarDB） |

**核心结论**：当前 SQLite WAL 方案满足仓库内确定性评测；PostgreSQL 路径已有代码与 SQL profile，
但迁移仍需要托管实例、权限、数据迁移、性能与回滚验收，不能简化为只改连接串。
