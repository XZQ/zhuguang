## 1. 执行摘要

本次改造不更换“连锁便利店异常闭环巡检”选题，重点把项目从“覆盖多个异常类型的流程演示”升级为“围绕冷柜失温事件的真实、安全、可运行、可验证多 Agent 闭环”。

核心调整如下：

1. 保留“逐光（店巡 Agent）”和冷柜、缺货、价签三类代码能力，采用“冷柜首要完整验证，缺货与价签补充展示”的一主两辅结构。
2. 保留 5 个业务 Agent，但重新强化职责分离、最小权限和独立验证。
3. 统一采用“5 阶段业务闭环 + 阶段内运行状态 + 官方 8 项能力检查”的三层模型。
4. 将静态 CSV 演示改造成可被工具真实查询和修改的有状态 Mock 业务系统。
5. 将“动作调用成功”与“业务结果验证成功”严格分离。
6. 优先实现风险遏制、商品批次隔离、设备维修、人工审批和双重验证。
7. 将跨店对标从“根因结论”调整为“诊断证据之一”。
8. 将 RAG、回滚、Trace、AgentTeams 等能力从文档声明改为真实运行证据；来不及实现的能力明确标为规划。
9. 形成可重复运行的场景集、自动化测试、评测指标和 evidence 证据目录。
10. 最终按实际实现统一更新 01～07、README、PPT 和 Demo 视频口径。

本次改造的北极星问题是：

> 一次门店异常是否被正确识别、及时遏制、真实处置，并由独立证据安全关闭？

## 2. 改造目标与非目标

### 2.1 业务目标

- 将冷柜异常发现后的安全遏制时间压缩到可量化范围。
- 降低错误关闭、未经审批写操作和不安全商品放行风险。
- 打通 IoT、设备、库存批次、POS、审批、工单和知识库之间的协同链路。
- 让总部运营、门店员工、维修商和食品安全角色在同一事件上下文中协作。
- 为便利店、超市、餐饮、药房等连锁业态提供可复用的异常闭环基础设施。

### 2.2 比赛目标

- 满足至少 3 个不同职能 Agent 的硬性要求。
- 以 AgentTeams 作为真实协同基点，而非只保留 YAML 或概念映射。
- 完整展示任务拆解、上下文传递、协同执行、状态追踪和异常分支。
- 提供可执行 AgentTeams 代码包、可运行 Demo、运行说明和运行证据。
- 形成核心 Skill 的输入输出、失败处理、安全边界、版本和验证材料。
- 提供至少一个真实 MCP 调用链或等价的可验证工具链。
- 提供 Trace、日志、评测结果、审批记录和业务结果验证证据。

### 2.3 工程目标

- 一条命令生成确定性场景数据。
- 一条命令运行本地端到端 Demo。
- 一条命令运行测试和评测。
- 在具备 Docker、Kubernetes 和 AgentTeams 的环境中可按文档部署。
- 相同 seed 下产生相同输入、预期分支和可比较结果。
- 所有写工具具备幂等键、审计记录和明确的补偿或回滚语义。

### 2.4 非目标

- 复赛阶段不建设完整商业化 SaaS。
- 不删除缺货和价签能力；复赛阶段不要求三个场景达到完全相同的实现深度。
- 不为了展示技术栈而强行接入全部推荐云产品。
- 不承诺未经真实实验验证的损耗下降和人效提升比例。
- 不允许 LLM 直接判定食品安全放行。
- 不实现付款、赔付、供应商结算等不可逆财务动作。
- 不以自动审批、伪造 Trace 或静态报告替代真实运行证据。

## 3. 设计原则

### 3.1 价值单位是“安全关闭的事件”

Agent 数量、Skill 数量、工具数量和 Trace 数量均不是最终价值。系统价值以正确关闭的 Incident Case 为单位。

一个事件只有同时满足以下条件才允许关闭：

- 风险已被遏制；
- 根因或可接受的处置依据有证据支撑；
- 执行动作已经改变真实业务状态；
- 设备恢复结果经过重新查询；
- 受影响商品已经安全放行、转移或报损；
- 审批、人工确认和工具调用证据完整；
- 独立验证者确认通过；
- 复盘和知识沉淀完成或明确跳过原因。

### 3.2 规则负责确定性，Agent 负责不确定性

- 温度阈值、库存为零、价签不一致等由规则或流处理检测。
- Agent 负责证据收集、假设排序、任务协调、冲突处理和异常分支。
- 金额阈值、权限、食品安全规则由策略引擎决定，不交给 LLM 自由判断。
- LLM 输出必须经过结构化 Schema 校验和策略校验。

### 3.3 遏制优先于完整诊断

冷柜失温属于风险随时间扩大的场景。系统不应等到根因完全确认后才行动。

允许预授权的低风险遏制动作包括：

- 通知门店员工；
- 请求现场测温、门体检查和照片；
- 对受影响批次设置临时停售；
- 将商品转移至已确认温度合格的备用冷柜；
- 创建维修工单草稿；
- 升级总部食品安全负责人。

完整诊断、维修审批和商品处置可以并行继续。

### 3.4 执行者不能自行宣布成功

Executor 只负责执行动作并返回执行回执。Auditor 必须通过重新查询业务数据、人工证据和策略规则独立验证结果。

### 3.5 设备恢复与商品安全分开建模

冷柜恢复正常不代表柜内商品自动安全。

系统必须按业务实体分别维护：

- asset_states：每台设备的状态；
- batch_dispositions：每个商品批次的隔离、转移、放行或报损状态；
- sales_holds：每个批次或 SKU 的 POS 限售状态；
- approvals：每个受控 Action 的独立审批状态；
- workorders：每张维修工单和对应服务商状态。

IncidentCase 上只保存由这些实体计算出的聚合结果。设备与商品风险均完成处置后进入 RESOLVED；复盘和证据归档完成后再进入 CLOSED。

### 3.6 回滚与补偿必须区分

- 改价等可逆动作可以回滚。
- 工单创建、通知发送通常采用补偿动作，不是物理回滚。
- 食品安全停售不能因设备温度恢复而自动回滚，必须经过独立验证和授权放行。
- 商品报损属于不可逆动作，必须人工审批并保留证据。

### 3.7 所有能力声明必须有证据等级

统一使用以下口径：

| 等级 | 定义 | 文档写法 |
|---|---|---|
| 已实现 | 代码存在，测试通过，Demo 中真实调用 | 已实现 |
| 模拟实现 | 使用有状态 Mock 完成真实输入输出和状态变化 | 模拟实现 |
| 规划 | 只有设计或接口，尚无可运行证据 | 规划 |

## 4. 改造前基线与核心差距

### 4.1 当前可保留能力

- 5 个业务 Agent 的角色框架已经建立。
- 已有异常检测、跨店对标、根因分析、补货、价签、工单和复盘代码骨架。
- 已有 Python 本地 Demo、MCP Server、Trace 和 SQLite 知识存储。
- 已有 01～07 文档、PPT、PDF 和 AgentTeams YAML。
- 已有三类模拟数据和基础报告页面。

### 4.2 当前必须修复的问题

| 问题 | 当前表现 | 影响 | 目标状态 |
|---|---|---|---|
| 场景缺少主次 | 冷柜、缺货、价签平均分配展示篇幅 | 每条链路都难以讲深 | 冷柜完整验证，缺货与价签补充展示 |
| 根因推断过强 | 跨店正常直接推断压缩机故障 | 不符合因果证据要求 | 输出 Top-K 假设和证据缺口 |
| 冷链处置不安全 | 提议移至常温待售区 | 存在食品安全风险 | 隔离、停售、合规转移或报损 |
| 验证不真实 | 检查动作记录即判定 resolved | 不是业务结果验证 | 重新查询 IoT、POS、库存和工单 |
| 审批被模拟为自动通过 | 默认 approved | 无法证明人机协同 | 支持 pending、approved、rejected、timeout |
| 回滚未进入编排 | 工具存在但主流程不调用 | 文档声明与事实不符 | 在失败场景执行补偿或回滚 |
| RAG 未检索 | rag_hits 始终为空 | 知识飞轮未闭合 | 诊断前真实检索并记录引用 |
| 复盘结构错误 | 多异常复用第一根因、误读 validation | 报告不可信 | 按 anomaly_id 关联各阶段产物 |
| 状态模型过于线性 | 一个 TaskContext 驱动多个异常 | 无法表达并发和等待 | Incident + Subcase + 多维子状态 |
| 数据快速过期 | 依赖固定日期和当前时间 | Demo 结果不稳定 | anchor-time、seed、预期断言 |
| AgentTeams 证据不足 | 本地主流程是 Python 类顺序调用 | 不能证明真实协同 | 真实 Team Room、委派消息和运行 Trace |
| 工程声明过度 | README 声称全跑通、RAG 和云栈已实现 | 评审追问风险高 | 按证据等级统一口径 |

### 4.3 评委反馈专项改造结论

| 评委方向 | 仓库内已完成 | 仍需外部证据 |
|---|---|---|
| 真实 AgentTeams 协同 | 运行证据 Schema、语义校验器、成功/失败双分支、Skill 包 provenance、MCP Span 关联和安全负向门禁 | Team Room、真实 Worker 委派、平台 Trace 与同一事故的动态导出 |
| PolarDB 双底座 | StateStore 协议、SQLite/PG 工厂、懒加载 psycopg 后端、四类迁移 profile、Kubernetes overlay | 托管 PolarDB 实例实跑、连接池/容量/性能与故障演练 |
| pgvector 知识飞轮 | pending 候选、独立人工审核、脱敏门、发布检索、来源引用、Recall@K/MRR | 真实复盘语料、真实门店命中率和复测改善率基线 |
| 冷热分层 | 审计月分区、受限分区维护函数、只复制且复核目标数量的外部表归档函数 | OSS/`oss_fdw` 外部表、真实归档与恢复演练；当前不删除源分区 |
| 库层权限 | 数据库登录账号绑定 principal scope、RLS、供应商总部可见、业务只读角色、最小 GRANT | 真实账号/租户/门店的正负向 SQL 证据与密钥轮换 |
| 23:00 复盘 | `pg_cron` 只将租户复盘写入 `review_jobs`，并提供 `cron.job_run_details` 健康视图 | 托管实例扩展可用性、告警接入和 Worker 消费运行记录 |

结论口径是“代码与静态/本地契约已实现，云资源运行外部待验证”。没有实例、凭证和真实数据时，不把 SQL 文件或测试替身写成云上已跑通。

## 5. 目标产品定位与场景范围

### 5.1 对外定位

建议统一使用以下表述：

> 逐光是面向连锁门店的异常闭环基础设施（产品能力描述：店巡 Agent），通过 AgentTeams 组织证据收集、风险诊断、安全处置、独立验证和经验沉淀；首个深度验证场景为便利店冷柜失温事件。

### 5.2 目标用户

- 连锁便利店总部运营负责人；
- 区域督导；
- 门店店长和现场员工；
- 食品安全或质量负责人；
- 设备维修服务商；
- IT、数据和审计团队。

### 5.3 首要完整验证场景

冷柜持续超温，系统需要完成：

- 告警可信度检查；
- 受影响设备和商品批次识别；
- 风险遏制；
- 多假设根因诊断；
- 门店人工协同；
- 维修商工单协同；
- 维修、调拨、报损审批；
- 设备恢复验证；
- 商品安全处置验证；
- 审计报告和经验沉淀。

### 5.4 补充展示场景

缺货继续保留独立运行能力，同时在冷柜主故事中作为级联影响出现：

- 商品被隔离后产生可售库存不足；
- 系统评估备用库存、附近门店库存和调拨方案；
- 调拨失败时生成补货建议。

价签异常继续保留独立运行能力，并作为补充 Demo 展示：

- 可逆写操作；
- 幂等控制；
- 审批；
- 真实回滚。

## 6. 统一流程模型

### 6.1 三层模型

项目统一采用以下三个层次：

1. 5 阶段业务闭环：用于 PPT、README、业务说明和总览。
2. 阶段内运行状态：用于代码、事件流、异常分支和 Trace。
3. 官方 8 项能力：作为覆盖检查项，不强行建成 8 个串行状态。

### 6.2 五阶段业务闭环

| 阶段 | 业务目标 | 主要输出 |
|---|---|---|
| 1. 发现与遏制 | 确认事件、评估风险、阻止损失继续扩大 | Incident、初始证据、遏制动作 |
| 2. 诊断与决策 | 构建假设、补齐证据、形成处置计划 | Top-K 假设、证据矩阵、决策计划 |
| 3. 处置执行 | 完成审批、人工协同、维修和业务变更 | 审批记录、工单、状态变更回执 |
| 4. 独立验证 | 重新查询设备和业务状态，决定通过或重开 | 验证报告、reopened 或 verified |
| 5. 复盘演进 | 生成复盘、知识入库、评估 Skill 改进 | 复盘报告、知识引用、评测指标 |

### 6.3 官方八项要求映射

| 官方要求 | 五阶段映射 | 证据 |
|---|---|---|
| 任务输入 | 阶段 1 | 告警、人工触发、计划任务 |
| 任务拆解 | Orchestrator 贯穿各阶段 | 子任务 DAG、委派消息 |
| 上下文传递 | 全阶段 | IncidentContext、引用和事件日志 |
| 工具调用 | 阶段 1～4 | MCP 请求、响应、request_id |
| 结果验证 | 阶段 4 | 重新查询后的验证报告 |
| 执行证据沉淀 | 全阶段 | Trace、日志、审批、截图、报告 |
| 审批与回滚 | 阶段 3～4 | 决策票据、补偿和回滚记录 |
| 经验沉淀 | 阶段 5 | 知识条目、RAG 引用、Skill 建议 |

### 6.4 主阶段与阶段内状态

业务阶段使用稳定枚举：

    DETECT
    DIAGNOSE
    ACT
    VERIFY
    LEARN

Incident 生命周期状态使用：

    OPEN
    CONTAINED
    RESOLVED
    CLOSED

阶段内工作状态使用：

    NOT_STARTED
    RUNNING
    WAITING
    FAILED
    DONE

业务实体状态独立维护：

    asset_states[asset_id]:
      abnormal | uncertain | recovering | recovered | failed

    batch_dispositions[batch_id]:
      unknown | quarantined | transferred | released | disposed

    sales_holds[batch_id]:
      inactive | active | release_pending | released

    approvals[action_id]:
      not_required | pending | approved | rejected | timeout | cancelled

    workorders[workorder_id]:
      created | assigned | in_progress | done | failed | cancelled

IncidentCase 可以派生 containment_state 和聚合健康状态，但不得用一个标量覆盖多个批次、审批或工单的不同结果。

### 6.5 关键状态约束

- 创建 IncidentCase 后进入 phase=DETECT、incident_status=OPEN，完成 triage 才能进入后续阶段。
- 高风险冷链事件必须在完整诊断前进入 incident_status=CONTAINED，或明确记录无法遏制原因和升级动作。
- 每个受控 Action 的 approval 未 approved 时禁止执行该 Action。
- workorder 为 done 不代表对应 asset 已 recovered。
- asset recovered 不代表相关 batch 可以 released。
- 每个 batch 的 released 必须有 Auditor 验证、策略依据和授权证据。
- VERIFY 失败时记录 reopened 事件，将 incident_status 退回 OPEN 或 CONTAINED，并将 phase 迁移到 DIAGNOSE 或 ACT。
- 所有设备和批次达到允许的终态后，incident_status 进入 RESOLVED。
- LEARN 完成或记录明确跳过原因后，incident_status 才能从 RESOLVED 进入 CLOSED。

## 8. Agent 拓扑与职责调整

### 8.1 实体口径

- 1 个 AgentTeams Framework Manager；
- 5 个业务 Agent；
- 共 6 个运行实体，但业务 Agent 数量统一写 5。

Framework Manager 不计入业务闭环角色，不应与 Orchestrator 重复描述。

### 8.2 目标拓扑

    Admin / Human Operators
        |
    AgentTeams Manager
        |
    Incident Orchestrator / Team Leader
        |-- Sentry / Evidence Triage
        |-- Diagnoser / Hypothesis Analysis
        |-- Executor / Controlled Action
        |-- Auditor / Independent Verification

### 8.3 角色矩阵

| Agent | 核心职责 | 关键输入 | 关键输出 | 权限 |
|---|---|---|---|---|
| Orchestrator | 拆解、调度、状态追踪、超时和冲突仲裁 | IncidentCase | 子任务、阶段迁移、升级 | 工作流状态读写；业务系统只读，禁止直接业务写 |
| Sentry | 事件分级、证据采集、证据质量评估、提出遏制请求 | 告警、IoT、资产数据 | 初始证据包、severity、containment_request | 业务系统只读 |
| Diagnoser | Top-K 假设、证据矩阵、下一步检查 | Evidence、Runbook、历史案例 | Hypotheses、check plan | 只读 |
| Executor | 策略检查、审批、工单、停售、转移、放行执行和补偿 | Decision、approval | Action records | 受控业务写；无权自行决定放行或关闭 |
| Auditor | 独立重查、设备与商品双重验证、复盘 | Action、最新业务状态 | Verification、release_recommendation、review | 全域只读，受控知识写 |

### 8.4 协作规则

- Orchestrator 只调度，不替 Worker 执行领域任务。
- Worker 产物必须写入共享 IncidentContext，并附 Schema 版本。
- Agent 间传递引用，不复制超大原始数据。
- Diagnoser 无权直接调用写工具。
- Executor 无权将 Incident 标为 RESOLVED 或 CLOSED。
- Auditor 不读取 Executor 的布尔结论作为唯一验证依据。
- Sentry 只生成 containment_request，由 Orchestrator 委派 Executor 执行预授权遏制。
- Auditor 只生成 release_recommendation；策略或人工批准后，由 Executor 执行解除停售。
- 所有等待状态必须包含 owner、deadline 和 timeout_action。
- 多个子任务允许并行，但每个 Action 必须有唯一 idempotency_key。

### 8.5 唯一业务核心与双运行入口

领域模型、状态存储、PolicyEngine、Skill 和 MCP 构成唯一业务核心：

    IncidentService
      |-- domain models
      |-- state_store
      |-- policy
      |-- skills
      |-- MCP tools

本地 Demo 和 AgentTeams 只是两个 Adapter：

    demo/run_demo.py
      -> LocalDemoAdapter
      -> IncidentService

    AgentTeams Team Leader / Workers
      -> AgentTeamsAdapter
      -> IncidentService

约束：

- IncidentService 是阶段迁移和业务状态的唯一事实写入入口；
- 本地 Demo 不维护第二套 Incident 状态机；
- AgentTeams Team Leader 负责任务委派，领域状态仍通过 IncidentService 更新；
- 两个入口使用相同 scenario、Skill、MCP、Policy 和验证逻辑；
- 只有 AgentTeams 入口产生的真实委派消息可以作为 AgentTeams 协同证据；
- 本地 Demo 用于快速回归和无 AgentTeams 环境下的确定性验证。

## 9. 冷柜失温首要完整验证场景

### 9.1 场景初始条件

示例事件：

- 门店：S03；
- 设备：FROST-S03；
- 连续 30 分钟温度高于业务阈值；
- 门磁显示近期频繁开启；
- 压缩机电流数据部分缺失；
- 柜内有 3 个冷藏商品批次；
- 门店员工尚未确认现场状态；
- 维修预算可能超过审批阈值。

### 9.2 阶段 1：发现与遏制

Sentry：

1. 校验告警时间窗和数据新鲜度。
2. 查询主传感器和备用传感器。
3. 查询门磁、供电、环境温度和设备运行状态。
4. 查询受影响商品批次和储存要求。
5. 生成初始证据包和 severity。
6. 对高风险事件生成 containment_request，由 Orchestrator 立即委派 Executor 执行预授权遏制：
   - 通知店员；
   - 请求手工测温和照片；
   - 设置相关批次临时停售；
   - 查找备用冷柜容量。

验收条件：

- containment_state 为 active，或有明确失败原因和升级记录；
- Evidence 包含 source、observed_at、freshness 和 request_id；
- 无需等待维修审批即可完成低风险安全遏制。

### 9.3 阶段 2：诊断与决策

Diagnoser：

1. 加载当前设备型号的版本化 Runbook 和 Policy（P0 配置能力）。
2. 若启用 P1 RAG，则检索历史同类事件。
3. 生成 Top-K 假设。
4. 为每个假设列出支持证据、反证和缺失证据。
5. 若启用 P1 cross-store-benchmark，则调用跨店对标识别共同因素或单店因素；P0 不以此为前置依赖。
6. 请求补充证据，例如现场测温、门体照片、压缩机电流。
7. 形成处置建议和风险说明。

Orchestrator：

- 判断是否等待人工证据；
- 对超时未响应门店升级区域督导；
- 在诊断继续进行时保持遏制状态；
- 将决策任务分派给 Executor。

验收条件：

- 至少输出 2 个候选假设；
- 最高置信度结论必须引用证据；
- 缺少关键证据时不得输出“已确认根因”；
- 若启用 P1 RAG，命中必须包含 knowledge_id 和引用片段；P0 未启用时明确记录 disabled，不伪造命中。

### 9.4 阶段 3：处置执行

Executor 根据策略执行：

预授权动作：

- 通知；
- 临时停售；
- 创建工单草稿；
- 转移到本店已验证合格的备用冷柜。

需审批动作：

- 超预算维修；
- 跨店调拨；
- 大额报损；
- 商品销毁；
- 解除食品安全停售。

禁止动作：

- 自动付款；
- 绕过审批；
- 无证据放行商品；
- 修改审计日志；
- 将冷藏商品移至不合格常温区域。

支持的审批分支：

- approved：继续执行；
- rejected：保持遏制并升级；
- timeout：保持遏制，通知上级，不自动执行；
- cancelled：记录原因并执行补偿。

验收条件：

- 所有写操作具备幂等键；
- Action 保存 request、response、approval_id 和审计时间；
- 工具超时不会导致重复写入；
- 补偿或回滚动作可被主编排调用。

### 9.5 阶段 4：独立验证

Auditor 必须重新调用工具验证：

设备维度：

- 多个连续采样点恢复到业务范围；
- 备用传感器与主传感器差异在允许范围；
- 设备运行状态正常；
- 工单状态为 done 且有完成证据。

商品维度：

- 计算各批次累计时间—温度暴露；
- 确认商品仍在隔离、已转移、已报损或符合放行条件；
- POS 售卖限制状态与商品处置一致；
- 放行必须有人工或策略授权。

闭环维度：

- 审批证据完整；
- 没有未完成高风险 Action；
- Trace 包含关键 Agent、Skill、MCP 和人工节点；
- 验证者与执行者身份不同。

失败处理：

- 设备未恢复：回到 DIAGNOSE 或 ACT；
- 设备恢复但商品不安全：保持停售，进入商品处置分支；
- 工具数据不一致：标记 uncertain，要求人工复核；
- 维修商状态与 IoT 不一致：以独立业务数据为准并升级。

### 9.6 阶段 5：复盘演进

Auditor：

1. 按事件时间线生成复盘。
2. 为每个异常和商品批次关联正确根因、动作和验证。
3. 记录本次诊断使用的知识条目。
4. 生成新的知识候选条目。
5. 通过去重、置信度和人工审核门槛后入库。
6. 输出 Skill 更新建议，但不自动修改生产 Skill。

验收条件：

- 知识条目引用真实 Evidence 和 Trace；
- 下一次同类场景可以检索该条目；
- 复盘不再复用第一条根因；
- 低置信度经验进入待审核区。

## 10. 异常与失败场景

复赛 P0 评测固定覆盖 6 个确定性场景：A 压缩机故障、B 传感器误报、C 门未关闭、D 审批超时、E 设备恢复但商品不可放行、F 工单查询部分失败。A～C 验证可安全关闭路径，D～F 验证等待、阻断和回开路径。P1 的 20 场景扩展不得阻塞 P0 提交。

### 10.1 场景 A：压缩机故障

- 主备传感器均超温；
- 压缩机电流异常；
- 其他门店同型号设备正常；
- 维修审批通过；
- 设备恢复；
- 商品部分转移、部分报损；
- 最终关闭。

### 10.2 场景 B：传感器误报

- 主传感器超温；
- 备用传感器和人工测温正常；
- 设备运行正常；
- 保持短时遏制；
- 创建传感器校准工单；
- Auditor 确认误报并生成 release_recommendation，经策略或人工批准后由 Executor 解除停售。

### 10.3 场景 C：门未关闭

- 门磁持续打开；
- 温度升高；
- 压缩机工作正常；
- 门店员工关闭柜门；
- 温度恢复；
- 商品暴露时间仍需单独评估。

### 10.4 场景 D：审批超时

- 维修预算超阈值；
- 审批保持 pending 并最终 timeout；
- 系统不执行受控维修；
- 保持商品隔离；
- 升级区域负责人；
- Incident 保持 WAITING，不得伪造 closed。

### 10.5 场景 E：设备恢复但商品不可放行

- 维修完成且温度恢复；
- 商品暴露时间超过策略阈值；
- 受影响批次的 batch_disposition 保持 quarantined；
- 需要人工报损审批；
- 证明设备恢复与业务安全是两个闭环。

### 10.6 场景 F：工单查询部分失败

- Executor 已有维修动作和工单引用；
- Auditor 独立调用 `query_workorder` 得到 `partial`；
- 动作回执不能替代业务状态查询；
- 事件回到 EXECUTE，work_status 为 BLOCKED；
- 保持停售和商品隔离，不得错误关闭。

## 11. Skill 改造方案

### 11.1 Skill 唯一事实清单

复赛目标共 9 个 Skill，其中 P0 核心 6 个、P1 增强 1 个、P2 补充场景 2 个。所有文档、Worker ZIP 和配置以此表为准。

|---|---|---|---|---|---|
| anomaly-detect | 通用闭环 | Sentry | P0 | 是 | 改造 |
| coldchain-risk-assess | 冷链领域 | Diagnoser | P0 | 是 | 新增 |
| rootcause-drilldown | 通用诊断 | Diagnoser | P0 | 是 | 改造 |
| work-order-dispatch | 受控执行 | Executor | P0 | 是 | 改造 |

## 12. MCP 与有状态 Mock 工具改造

### 12.1 目标

MCP 工具不再只读取静态 CSV 或返回成功记录，而是对同一个有状态业务世界进行查询和修改。

本地使用 SQLite 保持零外部依赖；部署时可通过数据库 URL 切换到 PolarDB PostgreSQL，业务 Service 不感知方言：

      seed.json

      runtime.db

runtime.db 为运行时生成文件，不提交；仓库提交 seed 和 scenario 定义。

### 12.2 统一工具响应

所有工具返回统一 Envelope：

    ok
    data
    error
    request_id
    source
    source_ts
    partial
    audit_ref

### 12.3 查询工具

P0 固定为 5 个查询函数：

| 工具 | 用途 | 说明 |
|---|---|---|
| query_device_context | 一次查询温度序列、设备健康、门磁、供电和维护摘要 | 通过 facets 参数选择字段，避免拆成多个演示接口 |
| query_inventory_batches | 查询设备关联商品批次与储存策略 | 返回 batch_id 和 policy_ref |
| query_sales_holds | 查询批次或 SKU 的 POS 限售状态 | 用于独立验证 |
| query_workorder | 查询维修工单和服务商状态 | 工单完成不自动代表设备恢复 |
| query_approval | 查询指定 Action 的审批状态 | 每个 Action 独立审批 |

- `search_knowledge`：只检索已发布且脱敏通过的知识；

### 12.4 写工具

P0 固定为 7 个动作函数，共形成 12 个 P0 MCP 函数：

| 工具 | 调用者 | 用途 | 关键约束 |
|---|---|---|---|
| apply_sales_hold | Executor | 设置批次或 SKU 临时停售 | L1 预授权、幂等 |
| release_sales_hold | Executor | 按批准后的放行建议解除停售 | 必须携带 approval_id 和 verification_id |

| create_approval | Executor | 创建受控 Action 审批 | 默认 pending |

| record_manual_evidence | Human / ScenarioEngine | 写入现场测温、照片引用和说明 | 原文件不进入数据库 |

工单状态推进由 ScenarioEngine 或维修商模拟端完成，不暴露为业务 Agent 可自由调用的 update_workorder_state。

P2 补充场景沿用现有函数：

### 12.5 写工具约束

- 必须携带 idempotency_key；
- 必须校验调用者身份和权限；

- 工单完成只改变工单状态，不自动改变传感器状态；

## 15. PolarDB 双底座与知识闭环

### 15.1 双底座边界

| 后端 | 用途 | 当前状态 |
|---|---|---|
| SQLite | 零依赖、确定性 Demo、六场景评测和本地回归 | 已实跑 |
| PolarDB PostgreSQL | 托管部署、pgvector、RLS、分区、pg_cron 和外部归档 | 代码/SQL/overlay 已实现，外部待验证 |

业务层只依赖 `StateStoreProtocol`；`create_state_store` 根据数据库 URL 选择实现，PostgreSQL 驱动按需加载。SQLite 不被替换或伪装成 PolarDB，它继续承担无云环境的可复现评测。

四个迁移 profile 必须按 `core → security → cron → archive` 执行。远程 seed/reset 默认被 CLI 拒绝，只有显式 `--allow-remote-reset` 才能继续；集成测试还要求数据库名包含 `test` 和 `DIANXUN_ALLOW_TEST_DATABASE_RESET=1`。

### 15.2 pgvector 知识飞轮

知识状态机固定为：

```text
Auditor 创建 pending 候选
  -> 独立 Human/HQ Reviewer 审核并确认脱敏
  -> published + redaction passed
  -> Diagnoser 可检索并保留 incident/trace/evidence 引用
```

`knowledge_items` 包含租户去重键、置信度、脱敏状态、审核状态、来源事故/Trace/Evidence、embedding model 和审核责任人。Auditor 无权审核自己的候选；未审核、脱敏失败或低于置信度门槛的条目永远不进入检索。

三个 P1 MCP 默认为关闭：`search_knowledge`、`create_knowledge_candidate`、`review_knowledge_candidate`。SQLite 使用确定性 hash embedding 做契约测试；PolarDB 使用 pgvector；生产可通过 HTTPS 的 OpenAI-compatible endpoint 生成 embedding。检索评测输出 Recall@K 和 MRR，并强制标注“只针对调用方提供的标注集，不代表真实门店改善率”。

### 15.3 库层权限强制

- `dianxun_principal_scope` 以 PostgreSQL `session_user` 绑定租户、角色和门店，不信任客户端可伪造的 session GUC；
- 核心业务表启用并强制 RLS；供应商合同仅 HQ 可见；
- `dianxun_business_ro` 只有业务查询表的 SELECT；运行账号没有 DELETE，故障注入表的 INSERT 只给 HQ；
- principal scope 的写权限对运行、HQ 和业务只读组角色全部撤销，只能由迁移/安全管理员配置；普通租户 HQ 不能跨租户，只有管理员显式登记为 `tenant_id='*'` 的独立全局管理账号才可跨租户；
- HTTP 层非回环无认证时拒绝启动，共享 Token 只能读，状态写必须是 Actor-bound Token；
- RLS/GRANT 是应用权限之外的第二道门，但真实数据库账号的正负向测试仍需目标实例完成。

并发副作用由数据库约束和条件更新共同防守：`approvals(action_id)`、`workorders(action_id)` 采用唯一索引，活跃停售对 `incident_id + batch_id` 采用部分唯一索引；审批决策/超时只更新 `pending` 行，解除停售只更新 `active` 行并检查影响行数，故障注入计数采用原子递减。同一 Action 即使换用新的幂等键，也不能创建第二张工单、第二份审批或重复活跃停售；这组约束已纳入 SQLite 对抗测试和 PostgreSQL 静态契约，真实多连接竞争仍需在目标 PolarDB 集成门禁中复核。

### 15.4 审计冷热分层

`audit_log` 按 `created_at` 月分区。`ensure_audit_partition` 只允许月首日期和有限维护窗口，运行账号不能任意建表。归档函数只接受 `audit_log` 子分区和已配置的 foreign table，复制后复核目标月份行数并写入 verified manifest；任何数量不一致都会回滚。

当前函数故意不执行 `DELETE`、`DROP TABLE` 或分区卸载。只有在 OSS 恢复演练、哈希/数量复核、留存审批和回滚方案全部通过后，才允许另行设计源分区清理流程。

### 15.5 23:00 复盘调度

`pg_cron` 每天 23:00 只向 `review_jobs` 幂等入队，不在数据库内执行 Agent、LLM 或外部 HTTP。外部 Worker 领取任务后仍走 AgentTeams、Skill、人工审核和 Trace。`dianxun_cron_health` 视图只向 HQ 暴露两项作业的 `cron.job_run_details`，供告警系统识别 failed、长时间 running 或静默缺跑。

### 15.6 证据与降级

- 无知识命中时明确返回 no hits；检索失败不阻塞先行停售；
- RAG 只能补充诊断证据，不能覆盖商品安全 Policy；
- 没有 `DIANXUN_TEST_POSTGRES_DSN` 时，两项 PolarDB 集成测试必须显示 skipped，不能改成假通过；
- 当前没有 PolarDB、OSS 或真实门店基线，因此只声明“实现可验”，不声明“云上运行”或“经营改善”。

|---|---:|
| 6 个确定性 scenario | 100% 通过 |
| 场景 A、D、E 本地 Demo | 100% 通过 |
| 未授权业务写操作 | 0 |
| 错误安全放行 | 0 |
| 错误关闭事件 | 0 |
| 同一 idempotency_key 的重复副作用 | 0 |
| 关键 Evidence 字段完整率 | 100% |
| 五阶段关键 Trace 覆盖率 | 100% |
| AgentTeams Worker 安装与真实委派烟测 | 至少 1 次完整成功 |
| 缺货、价签现有独立入口回归 | 均可运行并退出 0 |
| README 命令、实现状态与 evidence 不一致项 | 0 |

关键 Evidence 字段指 incident_id、source、observed_at、collected_at、request_id、quality 和 immutable_hash。任何 P0 门禁未通过时，不得将对应能力标记为“已实现”。

### 22.1 业务验收

- 冷柜异常可以被确定性复现。
- 高风险事件先遏制后诊断。
- 受影响商品批次可识别。
- 设备恢复和商品安全分别验证。
- 未经授权不能解除停售。
- 验证失败可以 reopened。
- RESOLVED 由 IncidentService 根据 Auditor 验证结果计算；CLOSED 在 LEARN 完成后由 IncidentService 迁移。

### 22.2 多 Agent 验收

- 5 个业务 Agent 职责和权限不同。
- Orchestrator 有真实委派记录。
- 上下文使用结构化 Schema。
- Worker 之间有可追踪交接。
- 人工等待和超时真实存在。
- Executor 不能自行关闭事件。
- Auditor 通过独立工具查询完成验证。

### 22.3 Skill 验收

- 每个核心 Skill 有 SKILL.md。
- 输入输出 Schema 可验证。
- 成功和失败样例齐全。
- 单元测试通过。
- 权限和失败处理明确。
- 有版本和变更记录。
- Worker 包内 Skill 可被 AgentTeams 加载。

### 22.4 工程验收

- 干净环境可按 README 启动。
- 数据生成、Demo、测试、评测均有明确命令。
- 所有命令检查最终退出码。
- MCP 查询和写入均有 request_id。
- 写操作具备幂等。
- Trace 可关联 Agent、Skill、MCP、审批和人工节点。
- SQLite 与 PostgreSQL 方言差异只存在于 StateStore 适配层。
- 知识候选未审核或未脱敏时不可检索，Auditor 不可自审发布。
- RLS 身份来自数据库登录账号；业务只读账号无写权限。
- pg_cron 只入队，归档只复制并复核，不自动删除源分区。
- 无真实密钥和隐私数据。
- Git 工作区最终只包含预期改动。

### 22.5 文档验收

- 01 正文不超过比赛限制。
- PPT 与实际页数一致。
- 5 阶段、8 项要求和运行状态不混用。
- 1 Manager + 5 业务 Agent 口径一致。
- 已实现、模拟实现、规划标注一致。
- 不再声称“跨店正常即证明压缩机故障”。
- 不再出现“冷藏商品移至常温待售区”。
- 不再用动作记录代替业务验证。
- 不把本地知识测试写成真实门店改善率，不把静态 SQL/YAML 写成云上已运行。
- 不再将未调用的自动回滚和云组件写成已完成。

## 23. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| AgentTeams 本机环境不可用 | 无法获得真实运行证据 | 使用官方 Cloud Studio，优先锁版本和包格式 |
| 时间不足 | 改造范围失控 | 严格执行 P0/P1/P2，优先完成冷柜主线，同时保留缺货和价签可运行入口 |
| LLM 输出不稳定 | Demo 不可复现 | 结构化输出、规则兜底、固定 seed 和模型参数 |
| 外部工具不可用 | Demo 中断 | 有状态 Mock + 故障注入 + 明确降级 |
| 食品规则不完整 | 安全边界不可信 | 将阈值外置为 SOP/Policy，禁止模型自由放行 |
| 文档再次过度声明 | 评审可信度下降 | 最终逐项对照运行证据更新文档 |
| 多状态组合过多 | 状态机爆炸 | 主阶段稳定，多维子状态独立建模 |
| 动态证据泄露密钥 | 安全风险 | 脱敏、Secret 注入、提交前扫描 |
| 无 PolarDB/OSS 测试环境 | 无法证明 SQL 在目标云产品实际运行 | 保留条件集成测试和明确 skip；在隔离测试库按 core/security/cron/archive 顺序验收 |
| RAG 指标被误写成经营收益 | 可信度下降 | 指标绑定标注集与样本量；真实门店改善率单独建立对照基线 |
| 官方用云 Skill 口径不一致 | 可能影响复赛合规判断 | 向组委会书面确认；若为硬门槛，只接入业务必要且可真实验证的官方 Skill |

## 25. 最终决策

本项目后续统一按以下决策执行：

- 不换题；
- 不追求更多 Agent 和更多云组件；
- 保留 5 个业务 Agent；
- 采用“冷柜首要完整验证 + 缺货、价签补充展示”的一主两辅结构；
- 保留冷柜、缺货、价签三类场景的独立运行能力；
- 使用 5 阶段业务闭环；
- 将官方 8 项要求作为横向检查项；
- 使用 phase + incident_status + work_status + 实体状态表达真实等待和并发；
- 商品批次、审批和工单按实体建模，不使用单一标量覆盖多个结果；
- IncidentService 是状态迁移和业务状态的唯一事实入口，本地 Demo 与 AgentTeams 仅作为 Adapter；
- 安全遏制优先于完整诊断；
- 执行动作必须改变业务状态；
- Auditor 必须重新查询并独立验证；
- 设备恢复与商品安全分别关闭；
- SQLite 用于确定性评测，PolarDB PostgreSQL 用于部署，两者共用 StateStore 契约；
- Auditor 只写知识候选，独立人工审核和脱敏通过后才可检索；
- 只有真实标注集检索才能声明 RAG 指标，只有真实门店对照数据才能声明改善率；
- pg_cron 只负责复盘入队，Agent/LLM 仍在外部 Worker；
- OSS 归档默认只复制并复核，不自动删除源分区；
- 只有真实 AgentTeams 运行才能声明协同落地；
- `qwen3.5-plus` 仅用于目标 AgentTeams，凭证运行时注入，费用与替代模型迁移成本必须披露；
- 当前 P0 为自定义 Skill，“官方用云 Skills”口径未确认前不得宣称完全满足；
- 所有文档最终以代码、测试和 evidence 为准。
