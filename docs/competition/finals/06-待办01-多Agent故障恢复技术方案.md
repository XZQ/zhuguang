## 1. 问题与目标

同一事件的巡检任务没有成功结果时，现有运行接口不会分配后续阶段。这能防止缺少证据却继续处置或放行，但如果 Worker 卡住、持续发送空心跳，或者主控没有调用重派，事件可能长期无法推进。

目标是让每个任务在可控时限内成功、重试或进入明确的异常处置状态。业务所需的前置证据仍必须满足；超时不能视为成功。恢复规则由服务端确定性执行，主控 Agent 负责业务判断和协作安排。

本文保留最初方案与基线差距。随后实现的实际接口、参数、兼容与回滚以[故障恢复运行手册](../../operations/runtime-recovery.md)为准；未引入工作流框架、依赖或新数据表，未部署。

## 2. 原基线架构与当时边界

外层是框架 Manager，五个业务角色中已经包含 Orchestrator 主控，因此不是“业务主控之外再加五个子 Agent”。

同一事件的运行步骤为：

`DETECT/Sentry → CONTAIN/Executor → DIAGNOSE_DECIDE/Diagnoser → EXECUTE/Executor → VERIFY/Auditor → RELEASE/Executor → FINAL_VERIFY/Auditor → LEARN/Auditor`。

主控通过运行接口分配任务；Worker 提交请求；服务端校验身份、范围、版本、租约和业务结果，持久化事件、回执与检查点。下一阶段通过快照取得共享结果。只有服务端核验成功才能写成功检查点；Worker 不能自报业务终态。

| 已有机制 | 当前限制 |
|---|---|
| 阶段前置检查和成功检查点 | 巡检未完成也挡住安全遏制；尚无独立应急分支 |
| 默认 60 秒任务租约、心跳续租 | 未看到独立执行硬截止和业务无进展超时；心跳仍可能续租 |
| 超时重派和唯一后继任务 | 需主控调用；运行接口把任务交回原 Worker 身份 |
| 持久化上下文、版本检查、旧租约拒绝 | 不能据此声称已有独立后台巡查、备用实例接管或主控自动恢复 |
| 工具权限、业务事务、幂等标识和回执 | 外部副作用在超时后是否已发生，仍需按工具契约核验 |
| 默认 24 小时上下文 TTL | TTL 是上下文有效期，不能代替任务超时、恢复调度和人工升级 |

## 3. 责任分配

### 3.1 服务端调度器

- 独立于模型调用运行，依据持久化截止时间、任务状态和恢复策略巡查任务。
- 自动失效超时任务、安排有限重试、记录升级事件；不依赖主控再次成功推理。
- 同时监督主控自身的编排任务。当前阶段表没有主控执行项，需要单独建模其任务身份、租约、截止时间与恢复记录，不把主控塞进业务八步链。
- 多调度器或重启恢复时，通过事务与版本条件竞争领取任务；同一次失效只能产生一个有效后继。采用周期性补扫覆盖通知丢失。
- 外部模型或工具调用不得长期占用数据库事务锁；短事务领取、事务外调用、短事务核验回执。实施前逐个梳理现有事务边界。
- 对调度器自身配置运行监督、健康检测和告警。独立进程不等于高可用；数据库或调度服务不可用时，暂停新增危险写操作并通过独立监测暴露故障。

### 3.2 主控 Agent

- 拆分业务任务、提出角色委派、解释异常与汇总结果。
- 不能修改截止时间来无限延期，不能绕过审批、证据或审计。
- 恢复后先读持久化快照并核对已分配任务，避免重复委派和重做副作用。

### 3.3 业务 Worker

- 在授予的角色、租户、门店和任务权限内工作，提交可核验的进展与结果。
- 配合取消；任务超时或失效后停止新操作。服务端仍必须拒绝迟到写入，不能只依赖 Worker 自觉退出。
- 备用 Worker 必须满足相同权限范围；审计独立性不能因故障恢复而降低。

## 4. 公共机制，按阶段和操作配置

| 策略 | 设计要求 |
|---|---|
| 排队监测 | 识别任务无人领取、无可用 Worker；不能反复派回无人消费的队列 |
| 心跳超时 | 发现断联；心跳只证明存活，不等于业务进展 |
| 单次执行硬截止 | 一次尝试最多运行多久；心跳与重复输出均不能延长 |
| 无进展超时 | 依据新证据、有效工具回执或可校验子步骤判断；重复发送相同内容不刷新 |
| 总恢复预算 | 包含排队、执行、退避和多次尝试的总时限；重启或换 Worker 不重置 |
| 数据新鲜度 | 检查采集时间、来源、缺失项；数据源停更不应被误判成 Worker 存活问题 |
| 有限重试 | 对临时网络故障、限流等按策略退避并加入随机抖动；权限错误、无效输入等不盲目重试 |
| 故障隔离 | 持续失败的 Worker 或上游暂缓接收新任务；限制重试并发，避免放大故障 |
| 异常升级 | 预算耗尽后持久化失败原因、责任人、处理期限与告警投递状态 |

策略按“角色＋阶段＋操作类别”选择，不能让 Executor 的查审批、创建工单、解禁共用一套重试规则。超时参数需要依据实际延迟分布、业务风险和演练确定；现有 60 秒租约不是所有步骤的推荐执行时限。

人工审批和现场维修使用显式等待状态：释放模型执行资源，保存等待对象和业务截止时间，由事件通知或有界轮询唤醒；逾期提醒、升级，不能循环创建审批或工单。等待截止与执行截止分开管理，定义与上下文 TTL 的关系，防止等待被 TTL 静默截断。

## 5. 五个角色的恢复策略

| 角色 | 故障处理 | 禁止行为 |
|---|---|---|
| 主控 Orchestrator | 调度器恢复编排任务；从快照读取当前阶段、有效委派和回执 | 自己卡住后只能等自己发现；重复分配同一阶段 |
| 巡检 Sentry | 有限重试读取；必要时换健康 Worker；数据源故障转证据不足和告警 | 把过期、缺失数据当作正常；超时后伪造检测成功 |
| 诊断 Diagnoser | 有限重试或替换诊断实例；保留证据引用；不确定时转人工研判 | 为推进流程编造根因；绕过执行权限自行处置 |
| 执行 Executor | 先核验回执；使用稳定幂等标识重试；审批进入等待状态 | 超时即认定未执行；重复下单、重复处置；未经批准解禁 |
| 审计 Auditor | 重试独立查询或换独立审计实例；证据不足保持限制并升级 | 超时视为通过；用 Executor 自报替代审计；提前关闭事件 |

## 6. 超时、重派与迟到结果

1. 调度器发现失效条件，使用服务端时间和版本条件原子失效当前任务，记录具体原因。
2. 若可能已有外部副作用，先进入“结果待核验”，查询同一幂等标识对应的实际回执。
3. 故障可重试且预算足够时安排后继任务；保留事件、阶段、前序任务、累计尝试次数和原始总截止。
4. 选择符合角色和范围要求的健康 Worker；没有候选者时明确进入等待容量或人工升级，不伪造重派成功。
5. 旧任务再提交时必须被拒绝。操作网关在发起副作用前验证有效任务；已经发出的外部操作不能保证因取消而撤销，必须对账。
6. 成功结果与检查点持久化后才能推进依赖阶段；失败、partial、待核验均不得写成功检查点。
7. 预算耗尽后记录异常处置状态，保留证据和已经生效的保护措施；人工恢复也走受审计的状态转换。

重试不能保证外部系统只执行一次。稳定幂等标识、回执查询和必要的补偿共同处理重复执行风险；不支持幂等或查询的工具应转人工核验。补偿不是自动解禁或撤销安全措施。

## 7. 安全遏制与依赖隔离

当前 DETECT 未成功时不能进入 CONTAIN。拟新增受控应急分支，避免巡检卡住同时延误必要保护，但不能直接跳过成功检查点。

- 根据独立可用的风险证据或预先批准的“数据失联”策略触发；单纯模型超时不自动等于食品风险成立。
- 仅授予 Executor 执行明确范围内的保护操作；复用业务服务、身份校验、幂等与审计。
- 应急记录与正常检测检查点分开；恢复后根据已经生效的保护回执补齐正常流程，避免重复操作。
- 解除限制仍需完整证据、必要审批和独立审计；应急路径不能成为放行捷径。
- 不相关事件、独立证据收集可以继续；同一事件中依赖失败阶段的分支保持阻塞。不得用“改成全部并行”规避真实依赖。

触发条件、授权范围和不可用时的人工响应流程，在该分支编码前需先具体化；本文不代表已获真实门店自动处置授权。

## 8. 拟改动数据与接口

字段命名在实施时沿用现有模型，本节明确必须表达的语义：

- 每次尝试：开始时间、硬截止、最后有效进展时间及证据、失败类别、取消/失效原因。
- 跨尝试：首次排队时间、总截止、累计次数、最大尝试次数、下次可运行时间、策略版本。
- 运行控制状态：排队、运行、重试等待、等待审批/维修、结果待核验、人工介入、成功或失败；这些与 Incident 业务终态分离。
- Worker 选择：角色与权限范围、健康状态、容量、故障隔离期限；不得在事件载荷保存 Token。
- 审计与告警：恢复事件、原任务与后继关系、执行者、原因、投递记录和去重标识。

运行接口需支持选择合规后继 Worker、读取恢复状态、报告可验证进度、等待/唤醒，以及受限的人工恢复。旧 Worker 默认策略由服务端补齐，不能靠客户端未传字段而绕过截止或预算。调度器使用专用最小权限身份，不冒充任意主控或绕开租户隔离。

## 11. 验收场景

| 故障注入 | 必须观察到的结果 |
|---|---|
| Worker 断联、停止心跳 | 在配置时限和扫描容差内失效；同一前序只产生一个有效后继 |
| 持续心跳、重复进度但没有结果 | 无法续期硬截止；无进展策略生效，最终退出恢复预算 |
| 上游采样停更 | 标识过期或缺失证据；不因换 Worker 而误判正常 |
| 主控卡住或重启 | 服务端恢复编排；已成功阶段不重复，现有委派不重复创建 |
| 两个调度器同时恢复 | 事务竞争收敛，唯一后继；没有双重执行权限 |
| 旧 Worker 迟到或取消无效 | 迟到提交被拒；已发出的外部操作进入回执核验 |
| 工单已创建、响应丢失 | 恢复使用同一幂等身份核验，不能重复创建工单 |
| 所有候选 Worker 不可用、上游持续故障 | 有界等待/重试后明确升级；告警重试可追踪，不发生重试风暴 |
| 长时间审批或现场维修 | 模型资源释放，原审批/工单保留；唤醒与截止有效，不静默过期 |
| 审计失败或 partial | 不解禁、不关闭、不写成功检查点；执行者不能替代审计者 |
| 应急遏制触发与正常巡检恢复竞争 | 保护操作幂等、记录独立，恢复汇合不跳过安全门 |
| 跨租户重派、越权人工恢复 | 请求被拒并保留必要审计，不泄露其他租户数据 |
| 调度器停机或数据库不可用 | 健康监测暴露故障；恢复后补扫，不丢任务、不扩大写权限 |
| 旧快照升级与版本回滚 | 缺省策略明确；不复活失效任务，不丢回执和恢复预算 |

本地测试使用可控时钟与故障注入；多实例和 PostgreSQL 并发需对应环境验证。真实 AgentTeams 的实例替换、身份注入、任务取消、外部工具回执及断网恢复需独立平台证据。最新本地验证记录与平台待验收项见运行手册；不新增部署完成声明。

监控至少覆盖排队年龄、超时原因、重试与预算耗尽、待核验数量、人工等待、扫描延迟和调度器健康。指标只用角色、阶段、故障类别等固定低基数标签；事件与 Worker 明细留在受控日志，不把租户、事件、Trace 或 Token 作为指标标签。

## 12. 官方资料与采用方式

以下官方网页于本轮讨论中读取；本文是结合本项目的设计建议，不是官方对本项目的认证或统一默认参数。

1. [Temporal：Detecting Activity failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures)：区分单次执行、包含重试的总时限和心跳超时；采用分层时限思路。排队超时需配合实际重路由策略，不能机械重入同一无消费者队列。
2. [LangGraph：Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)：重试、执行/空闲超时、重试耗尽后的恢复处理；采用职责分离与显式失败分支。其节点超时支持有异步等限制，不据此假设任意同步调用都能被安全强制终止。
