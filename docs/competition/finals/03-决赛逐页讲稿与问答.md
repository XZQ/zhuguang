# VeriAgent｜决赛逐页讲稿与问答

> VeriAgent 为本份决赛准备稿工作标题；仓库作品名仍为店巡 Agent，队名为逐光。最终标题与发布版本在交付时冻结。

对应[12页决赛工作稿](../../../ppt/finals.html)，2026-09-12版。陈述、演示与问答的正式时长待组委会通知。下面按内容模块练习，不能将旧复赛3+1分钟视作决赛要求。

## 1. 逐页讲稿

### P1｜项目介绍

各位评委好，我们是逐光队。VeriAgent 面向需要受控执行和独立验收的实体业务流程。我们以冷柜失温作为第一个验证场景，解决一个具体问题：冷柜修好了，柜里的商品是否就能继续售卖？我们的系统要求设备、商品和处置证据分别完成核验，才允许关闭事件。

### P2｜谁需要这个系统

总部运营、区域督导和店长现在往往需要在温度告警、群消息、工单和审批之间确认进展。维修回执只能说明维修动作，温度恢复只能说明设备状态。我们将这些事实关联到同一个事件，并把“商品是否可以放行”设为独立验收条件。高风险处置先审批，执行者的回执不能替代验收。

### P3｜实际架构

业务状态由 IncidentService 管理，Policy 约束权限和审批，StateStore 提供事务与持久化。我们提供本地确定性验证入口和 AgentTeams Worker 运行接口，两者接入同一业务核心。当前本地事务和HTTP路径已验证；真实 AgentTeams 动态协同、人员审批与外部系统接入，需要目标环境证据。不会将配置文件当作运行完成证明。

### P4｜五个角色

Orchestrator 协调阶段，Sentry 发现异常，Diagnoser 提出证据关联假设，Executor 在权限和审批范围内执行，Auditor 独立重查。框架 Manager 不计入这五个业务角色。角色设计的重点是动作权限和验收责任可追溯，不能让执行者通过一句“完成”绕过领域门禁。

### P5｜一条闭环

发现失温后先停售和隔离，避免继续暴露风险；随后评估各批次的超温暴露并提出诊断假设。维修和商品处置按策略申请批准。执行结束后，Auditor 查询设备、商品、停售和审批等事实，满足条件才关闭。复盘生成知识候选，经过审核和脱敏才能发布。

### P6｜正常和失败分支

我们验证了六个合成场景。前三个分别处理设备故障、传感器疑点和柜门未关；后三个处理审批超时、设备恢复但商品仍不安全、工单查询不完整。在失败场景中，“保持遏制”本身就是正确结果，不能为了演示一条绿线而强行关闭。本地工单查询不完整时会回到处置阶段并阻塞，等待补齐证据。

### P7｜Skill工程

六个 P0 Skill 都有输入输出 Schema、调用边界、失败示例和版本记录。以 coldchain-risk-assess 为例，它按批次评估超温暴露并提出建议，不直接写库存或放行。Registry 用名称、版本和摘要定位制品，Worker包固定来源，Trace记录实际使用的Skill版本。平台发现和调用这些Skill的过程还要在真实运行时核验。

### P8｜安全与恢复

写操作依次经过角色权限、策略审批、幂等和审计。解除停售必须获得相应批准，并通过Auditor核验。商品报损不能靠软件回滚恢复，因此审批在前。HTTP运行接口在查询不完整时保持遏制并重查；取得完整的失败核验后，才允许按权限开始新的处置轮次。真实维修取消和对账需要企业系统适配。

### P9｜验证结果

在本地临时 SQLite 和合成数据环境下，六个场景全部通过，45条证据记录和26个适用阶段Trace完整，未出现测试定义中的五类安全违规。完整测试的最新命令、日期及通过/跳过数见[测试覆盖矩阵](../../测试覆盖矩阵.md)，演讲前按冻结版本读取。原 09-12 准备稿中的 112/110/2 是当时快照。这些是有限样本下的工程结果，不代表生产准确率，也不是模型效果评测；本地评测不调用大模型。

### P10｜已完成的改进

我们根据反馈聚焦冷链闭环，补强了商品当前安全检查、独立验收和权限约束。最新修复还覆盖三个容易在现场暴露的问题：失败操作不能留下部分写入；响应丢失后可以取回原输出；完整核验失败后可以按权限重新处置。相应本地回归已经通过，真实平台恢复还需单独取证。

### P11｜如何复用

可以复用的是职责分离、证据关联、状态管理和受控验收方式。迁移到餐饮配送时，要替换交接批次、暴露规则和WMS接口；迁移到设备检修时，要替换诊断Skill、检修动作和复产条件。我们不承诺只换配置就完成所有行业适配，每个新领域都要重新验证。

### P12｜交付和下一步

目前我们提供可复核的业务核心、六场景验证、Skill与MCP契约以及Worker制品。下一步重点是取得真实AgentTeams协作证据，并与冷链合作方对接设备、库存和审批接口，建立真实试点基线。VeriAgent坚持的完成条件是：设备恢复不等于商品安全，事件只有在证据闭环后才能关闭。谢谢各位评委。

## 2. 演示操作与口播

优先展示A，再展示E；F作为失败处理或问答备用。命令见[执行清单](02-决赛准备执行清单.md)。现场若使用本地版本，开场明确“以下外部设备、维修和审批为合成场景，业务状态实际写入本地数据库”。

| 操作 | 口播 | 需要展示的证据 |
|---|---|---|
| 展示A初始状态和事件编号 | 同一事件关联设备、受影响批次、审批和工单。 | incident_id、批次、设备、初始状态 |
| 展示遏制和审批 | 系统先停售；维修和处置按策略申请批准。 | hold状态、审批对象与时间、动作结果 |
| 展示A独立验证和关闭 | 完成动作后由Auditor重新查询，再由领域服务判断是否关闭。 | 独立查询、处置结果、最终CLOSED、审计 |
| 切换E | 这里设备已经恢复，但商品仍不满足处置条件，事件保持遏制。 | 设备恢复、批次仍不安全、CONTAINED |
| 按需切换F | 查询不完整不等于成功。本地流程回到处置阶段并阻塞，保持停售。 | partial字段、result=reopened、CONTAINED/EXECUTE/BLOCKED |

E固定场景没有“继续处置直到关闭”的最终录像，不能口播成已关闭。恢复到关闭的机制由Worker运行测试证明；要现场展示这一整段，需录制对应的真实执行路径。

## 3. 评委问答

### 为什么需要多Agent，单Agent加权限工具不行吗？

单Agent也能使用权限和状态机工具。我们选择分离角色，是为了明确读取、执行和验收责任，并在运行接口上约束角色、scope和租约。价值要通过可追溯协作和失败处理来证明，不能仅用Agent数量证明。当前单身份消融验证的是本系统Policy的拒动边界，不能外推为所有单Agent方案都更差。

### 与普通工单系统有什么区别？

普通工单也可以配置审批和复验。我们的重点是将设备、商品、停售与处置事实关联到同一个事件，由独立核验条件决定能否关闭，并为工具失败、输出丢失和重新处置提供运行接口。实际优劣需要与合作方现有流程建立同口径基线比较。

### 哪些部分是大模型做的？

当前本地六场景评测不调用大模型，诊断是证据关联的确定性逻辑。AgentTeams目标部署声明了模型和Worker运行方式，但真实模型委派、工具选择、成本和效果须用目标平台日志证明。不能把本地6/6说成大模型准确率。

### Auditor自己判断错了怎么办？

Auditor不能只复述Executor结果，需要重新查询多个事实，数据不全则阻断。领域服务还检查当前商品状态、审批范围和版本。但独立查询也不能保证传感器和人工输入绝对正确，所以真实部署需要数据质量校验、独立测量和业务负责人批准的规则。

### 如何判定食品已经变质？

当前不做真实食品变质检测。实现按批次计算超温度分钟，并依据比赛示例策略给出处置建议。真实部署必须由专业方提供适用商品的阈值、验证数据和处置规则，不能拿合成阈值直接决定食品放行。

### 断网、超时、重复请求会怎样？

证据缺失时保持遏制；有幂等键和事务约束，已完成的阶段输出随checkpoint保存。HTTP运行接口开始新处置轮次需要完整失败核验、正确角色和版本，旧租约不能继续写。本地Adapter的F场景会记录reopened并回到EXECUTE/BLOCKED，不能把这个结果当作HTTP运行接口已重执行。本地HTTP和恢复回归已验证；现场平台的进程重启和网络故障需单独演练。

### 能支撑512设备、500ms或多行业吗？

目前不作这些性能与规模承诺。512设备是旧展示中的模拟网络，当前可复核基线是六个冷链场景。迁移需要替换领域契约、策略与接口并重建验证集。性能应在明确硬件、模型、负载和外部接口后测量分位延迟与失败率。

### 商业价值如何量化？

建议试点记录人工串联时间、误派工单、异常到遏制时间、证据完整率、处置成本和商品损耗，并与同口径基线比较。目前没有真实经营数据，因此不承诺下降百分比或投资回收期。

### 有哪些开源贡献？

公开仓库提供领域核心、六个P0 Skill契约、MCP接口、Worker包、测试、演练及部署说明。需要按固定版本复现和验证；正式Release、第三方采用和真实平台证据应分别列出，不能由源码公开推断生态已建立。

## 4. 技术问答补充

### 是否做了形式化验证？结构正确就能保证结果正确吗？

当前使用六个 Skill 的运行时 Schema、Policy、事务/幂等、独立核验和人工审批，没有形式化证明。结构正确不等于输入真实或模型语义正确；传感器、商品规则和真实人员仍须验证。细节见[验证机制](../../Agent验证机制.md)。

### SQLite 是否有 WAL、乐观版本和并发回归？

独立 ContextBus 使用 WAL/expected_version；业务 SQLite 不强制 WAL，但 Incident 有版本 CAS，RuntimeContext 与领域写共用事务，嵌套失败使用 SAVEPOINT 回滚。已有真实线程和多实例回归，生产高争用与托管 PolarDB 单独验收。见[一致性说明](../../分布式一致性方案.md)。

### HTTP 延迟、重试与审批超时怎么回答？

默认 32 个连接、10 秒绝对截止、1 MiB body 上限；超限/满载分别是 413/503。runtime 有有限重试、等待和未知回执升级，没有已实测 P99 SLA 或通用熔断器。审批 timeout 不等于人工 rejected，更不能当批准。见[MCP 可靠性](../../MCP延迟与可靠性.md)。

### RAG、真实 IoT 与覆盖率如何界定？

当前检索使用 embedding，本地默认确定性 Hash Embedding，也支持兼容 provider；没有 BM25 hybrid/reranker 的实跑基线。知识须先审核脱敏。IoT 在本地由有状态替身驱动，轮询/订阅协议及延迟待真实平台选择；不存在已验证的 30 秒全网巡检。12/12 是 P0 工具契约/路径映射，不是行覆盖率。更完整的工程和试点边界见[测试矩阵](../../测试覆盖矩阵.md)与[业务差距](07-待办02-真实场景差距与产品完善分析.md)。

## 5. 彩排通过条件

- 一次完整陈述能清楚说明用户、问题、核心机制、证据范围和下一步。
- 正式时长收到后再记录每段实际用时，预留切屏和失败处理余量。
- 主讲与操作者对每个按钮、命令、预期终态有一致理解。
- 任意展示数字均能找到来源；明确“已验证、模拟、规划”的区别。
- 断网时能打开PDF与本地报告；使用录像时明确说明是预先录制。
- 对不知道的问题直接说明目前证据与验证计划，不临场补造已实现能力。
