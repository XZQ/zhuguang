# 店巡 Agent 真实场景差距与产品完善分析

店巡 Agent 最值得解决的问题，是冷柜异常发生后，门店能否及时保护受影响商品、让正确的人完成处置，并用可靠证据证明事件可以结束。当前项目已经具备受控执行、独立回查和持久化业务状态的工程骨架；主要差距集中在真实证据、实物动作、人员履约与跨系统一致性，而不在于 Agent 数量。

本文作为**待办 02**，状态为**分析已记录，改动待实施**。分析日期为 2026-09-12，源码基线为 `55860ea`，沿用“先分析、不写代码”的边界。待办 01 的恢复方案单独保留。本报告按 9 月 21～22 日现场准备安排确定先后顺序，正式报到、答辩和交付时间仍以组委会通知为准，不据此改写历史赛事记录。

研究对象暂定为中国连锁便利店、生鲜超市的冷藏商品异常处置；尚未取得合作门店访谈、实际故障台账或运营基线。因此，下文明确区分已读源码事实、公开资料、典型情境推演与待现场确认事项。既有八月版[真实门店差距与演进路线](../../assessments/真实门店差距与演进路线.md)保留历史口径，本文在当前源码上补充具体断点，不重复引用旧测试数量或旧排期。

## 1. 从业务结果重新定义问题

### 1.1 一个清晰的产品目标

建议面向门店的表述为：

> 店巡 Agent 帮助连锁门店把冷柜异常变成有责任人、有处理时限、有实物和系统回执、可复核的处置事件。它先协助控制受影响商品，再组织排查、审批与维修；只有设备、商品和销售限制分别满足条件，事件才允许关闭。

“冷柜温度正常”只回答设备的一部分问题。“商品是否仍适合销售”“有没有真正停售”“谁确认完成了转移”是不同问题。食品卫生原则明确把恢复过程控制、隔离受影响产品、决定处置、查明原因和防止复发列为纠偏内容，而不只是消除告警。[^1]

在这个目标下，系统需要维护四条有关联但不能互相替代的状态链：

| 状态链 | 需要回答的问题 | 不能作为替代证据的信号 |
|---|---|---|
| 设备 | 故障是否解除，监测是否有效，稳定观察是否满足条件 | 告警消失、网关在线、维修工单被点“完成” |
| 商品 | 哪些批次和数量受影响，在哪里，如何处置，谁接收或销毁 | 柜温恢复、数据库里写了 transferred/disposed |
| 销售渠道 | 门店 POS、外卖、线上库存等相关渠道是否实际阻断风险销售 | 某一个接口返回成功、某张库存表变成停售 |
| 人员履约 | 谁接单、何时到场、做了什么、留下哪些可核验回执 | 已发送消息、模型说已通知、审批角色字符串存在 |

### 1.2 成功不等于“关闭数量更多”

优先级首先是避免未经授权或缺少必要证据的放行，其次才是缩短不必要停售、减少误派维修和降低人工负担。安全门禁不能被效率得分抵消；但“全部停售、永不放行”也不是有效产品，因为它会产生经营损失并最终被员工绕开。

产品应区分“已安全遏制”“设备已恢复”“商品处置完成”“事件行政归档”。当设备仍在维修、商品已经受控时，界面必须展示这个事实，而不是用一个完成率掩盖进展。可关闭和可归档的条件需事先定义；无须维修的告警排除也应有正式路径。

### 1.3 为什么需要 Agent，哪些地方不需要

阈值计算、权限判断、时限、审批绑定、幂等、状态转换和放行检查应由确定性程序执行。Agent 更适合在不完整信息中归纳候选原因、决定还缺什么证据、解释操作步骤、协调跨部门任务和生成有来源的复盘。

五个角色的价值在于职责和权限分离，不意味着每条温度读数都要调用五次模型。普通已知告警可走规则与既定流程，复杂例外才调用模型；执行与审计应保持独立授权。当前合成评测不能证明五 Agent 普遍优于单 Agent 或传统工作流，需要相同工具、权限、任务和预算下的公平比较。

对外同时保留“VeriAgent”的运行时定位时，建议采用两层叙事：**店巡是当前具体业务验证，VeriAgent 是沉淀其中的受控执行与可验证交接能力。** 不把跨行业迁移方向说成已落地产品。

## 2. 真实流程应覆盖到哪里

### 2.1 首个客户与使用者假设

适合优先验证的客户是已有冷柜监测、库存或工单基础，但告警后的处置仍靠多人手工协调的连锁企业。总部运营或质量管理可能是采购和治理方，店员、店长与维修服务商是执行方，食品安全负责人负责商品策略与关键审批。谁愿意付费、哪个岗位最耗时，目前仍需访谈验证。

如果一家门店连批次、设备标识和真实测温都没有，第一阶段应先建立最小台账与采集流程，不能承诺接上模型就自动闭环。设备多、告警多也不自动意味着多 Agent 有价值；要证明减少了哪些交接错误和重复工作。

### 2.2 典型事件的完整旅程

| 环节 | 一线实际工作 | 必须留下的结果 |
|---|---|---|
| 事前准备 | 设备探头登记、商品存储规则、班次与应急联系人、备用库位确认 | 经批准的策略和可执行责任链 |
| 发现异常 | 判断超温、数据失联、开门或除霜是否属于已知运行状态 | 数据质量、时间窗口、风险级别及受影响范围 |
| 先行保护 | 相关渠道停售、实体贴标隔离、必要时受控转移 | 每个渠道回查、现场确认、数量与库位 |
| 排查原因 | 查设备、历史、门状态、电源、人工复测；必要时派单 | 有支持和反证的假设、检查计划、接单情况 |
| 决定处置 | 按商品规则评估，授权人员批准转移、报损或放行 | 绑定批次、数量、证据版本和动作的审批 |
| 完成动作 | 转移并接收、销毁并留证、维修并复测 | 接收/销毁/维修回执，而非仅操作请求 |
| 独立核验 | 重查实物证据、系统状态、当前范围和其他未解除的限制 | 明确通过项、失败项、未知项及下一责任人 |
| 收尾复盘 | 对账、追溯异常期间已售商品、跟踪复发、审核知识候选 | 可导出的事件证据包与遗留事项 |

温度事故不是所有食品安全问题的总入口。包装破损、交叉污染、过期、来源问题或召回，即使温度正常也可能阻止销售；首个版本可不自动识别这些问题，但必须接受人工或其他系统发来的阻断信息，不能由冷链“通过”覆盖其他限制。[^1][^2]

## 5. 最容易被遗漏的真实情境

完整清单见[待办 02：场景与验收清单](08-待办02-场景与验收清单.md)，共 36 项，按触发条件、当前覆盖、正确结果与证据要求列出。它们是风险情境清单，不是已经发生在客户门店的事故，也不是新增测试已通过。

其中最值得先讨论的八项是：

1. **刚查到的其实是旧数据。** 网关在线但探头停更，审计看到最后几条正常读数；应输出证据不足，而不是把成功查询当恢复。
2. **一柜多商品、一商品多批次。** 商品存储要求不同，事故前后又有补货；受影响范围必须随事实演进。
3. **系统停售，线下仍在卖。** 收银只有 SKU、员工扫不到批次，或者外卖已有订单；应明确渠道和物理隔离的缺口。
4. **转移没有地方可去。** 备用冷柜已满、目标温度也异常，或只转移了一部分；不能批准后就写“已转移”。
5. **货已售出或被加工。** 仅检查柜内剩余库存不能解决过去已暴露的风险，需要流向追踪和食品安全负责人决定后续处置。
6. **人员不在场。** 店长休假、交班、夜间店员独自值守、维修商拒单；消息发送成功不是责任已接走。
7. **多个问题同时存在。** 停电同时引发多柜报警，或同批商品还在其他召回/质检限制下；一次事件结束不能解除所有限制。
8. **现场其实不需要维修。** 除霜、补货短时开门、员工关门即可纠偏；仍需证据核验，但不应为了满足流程硬建维修单。

## 6. 把“可查、可控”变成可验收的产品要求

### 6.1 可查：给出证据与变化过程

一个事件详情页至少要回答：异常何时发生、何时被系统收到；哪些设备和批次受影响；当前事实有哪些未知；为什么采取这项动作；谁批准；命令发出后外部系统和现场分别发生了什么；为什么现在可以或不可以关闭。

每次关键判断保存当时的证据快照、策略版本、适用对象和结论，而非只留下最终一段总结。证据更正采用追加与失效关系，不能覆盖历史。普通摘要可校验内容变化，但不能独自证明采集来源真实或抵抗管理员篡改。

### 6.2 可控：把权限落实到动作和对象

| 动作 | 默认控制建议 | 结果核验 |
|---|---|---|
| 查询、诊断建议 | 只读，限定门店和对象；结论保留来源 | 证据时效、完整性和适用性 |
| 停售、隔离 | 企业预先批准的范围和触发条件；支持人工接管 | 相关渠道回查与现场确认 |
| 转移、报损、放行 | 合格人员审批，绑定批次、数量、动作和证据版本 | 接收/销毁/商品评估回执；范围变化时原审批失效或重审 |
| 设备远程操作 | 仅已验证适配器和明确允许的操作；维修安全要求另行制定 | 设备回执、独立状态和稳定观察 |
| 改策略、发布知识 | 审核与版本管理，回归通过后生效 | 可回退、记录影响范围 |
| 对客通知、报告监管、付款 | 留在相应责任人的授权流程中，不由模型自主发起 | 人工审核与正式业务系统回执 |

人工接管要有所有权：接管后 Agent 不再并发执行写操作，交回前进行对账。信息不足时展示未知与处理期限；不能无限等待，也不能把未知折算成一个看似精确的低风险分数。

### 6.3 可执行：让店员知道下一步做什么

最小员工端不需要复杂驾驶舱。单个任务应呈现：对象和位置、风险原因、最紧急的一步、截止时间、确认入口、需要采集的证据，以及“做不了”的原因选择。例如无备用库位、无法找到商品、仪器不可用、职责不符、外部系统故障。

员工提交“做不了”后必须流转给明确的责任人，而不是只把状态变成红色。离线场景需有本地 SOP 和事后回填机制；是否建设离线 App 由试点条件决定，不能只给后台增加字段就宣称支持离线闭环。

### 6.4 可恢复与可验证

待办 01 解决“任务不能无限卡住”。待办 02 解决“任务恢复后，是否真的完成了正确的业务动作”。两者需共用任务、事件、回执和策略语义，验收时同时检查时限、权限与实物证据。

Audit 角色独立只是第一层。要防止“执行者写一个完成字段，审计者再读这个字段就通过”的循环证明：转移须有接收方证据，停售须有对应渠道状态，维修须有复测，放行须有当前批次的合格评估。

## 7. 实施优先级与范围控制

### 7.1 答辩前优先完成的最小可信版本

以下是待实施顺序，不是本轮编码授权，也不承诺在未知的平台接入条件下全部完成。

| 顺序 | 工作包 | 完成标准 | 对应差距 |
|---|---|---|---|
| A | 产品目标与证据口径统一 | 一句话目标、四条状态链、已实现/模拟/待验标识在讲稿和演示一致 | G11、G12 |
| B | 测量与商品建议门禁 | 时间窗口、数据覆盖、人工测温适用范围、未知结果通过反例测试 | G01～G04 |
| C | 回执与批次范围 | 明确转移/报损/放行的证据契约，支持数量、目的地和范围版本；迟到或不匹配回执不能通过 | G05～G07 |
| D | 待办 01 的公共恢复能力 | 卡死、假心跳、主控故障、回包丢失都有有界且可审计的处理 | G10 |
| E | 人工处置最小流程 | 至少能演示认领、提交证据、无法执行、超时升级和人工接管；真实身份与模拟身份标识清楚 | G08、G09 |
| F | 目标平台与场景取证 | 真实 AgentTeams 同一事件的委派、工具回执、审计和版本能对应；外部业务仍模拟时明确标注 | G11、G12 |

时间不足时优先完成 B、C 中会导致错误建议或虚假业务完成的缺口，并保留明确受阻状态。演示少一些分支，但每个分支的结果要可信。不要为了覆盖更多功能而削弱安全门或手工修改评测结果。

### 7.2 试点必需，不能在答辩前伪装完成

真实商品规则签批；设备和探头台账、校准、时间同步；至少一个实际销售渠道及库存/批次映射；真实班次、审批和维修履约；现场转移与隔离 SOP；真实数据下的误报、损耗、人工负担基线。

先采用影子模式：实际数据进入系统，建议与人工流程并行，系统不自主实施真实高风险动作。规则与回执验证后，再开放企业预授权的有限动作。缺乏真实门店时，以透明合成演练证明机制，不能把它称为客户试点。

### 7.3 暂缓的扩展

跨行业零修改复用、自动修改食品策略、统一大规模微生物风险模型、全店所有巡检问题、全自动召回和付款，以及大范围更换工作流底座。缺货与价签继续作为复用方向，主答辩先解释清楚冷链事件。

## 8. 现场最有说服力的演示与回答

### 8.1 建议演示的四段证据

| 演示 | 评委应看到什么 | 展示前提 |
|---|---|---|
| 正常故障处置 | 从异常、停售、审批、处置到独立核验；设备和商品状态分别变化 | 已有正常场景，冻结版本后重跑并标明外部模拟范围 |
| 设备恢复但商品不能放行 | 温度正常仍被商品或审批条件阻断；界面明确下一责任人 | 沿用已覆盖场景，不伪造关闭 |
| 旧证据或不完整转移回执 | 输入不合格时输出未知/拒绝，不被批准按钮直接洗成完成 | 对应 G02、G04、G05 改动及测试完成后才能作为能力演示 |
| Worker 卡死或响应丢失 | 硬截止、有限恢复、原回执找回与旧任务拒绝 | 待办 01 实施并取得相应环境证据后展示 |

若后两项尚未实现，应在改进路线中讲解，不能用预制动画标成现场系统能力。答辩时长未确定前不强行安排每段分钟数。

### 8.2 高概率追问与诚实回答

**为什么不只做一个规则引擎？** 安全边界确实由规则和业务服务执行；Agent 用于跨来源证据整理、例外处理与协作。价值要用减少交接遗漏和人工整理负担来验证。

**温度恢复为什么不能卖？** 温度只是当前设备观测。商品可能经历过不合格暴露、尚未完成评估，或仍被其他原因限制；需按商品规则和当前证据决定。

**怎么证明店员真的转移了商品？** 目标设计要求来源与目的库位、批次数量、接收人和测量证据；当前本地处置标志不足以独立证明，属于明确待完善项。

**怎么防止五个 Agent 一起认错？** 角色分离之外，还要防同源数据共同失效；关键判断需要可信测量和必要的人工复核，任何模型一致同意都不能代替证据。

**如果店长不回复或者平台断网？** 系统进入显式等待或人工接管，保存责任与截止，按预授权策略处理；相关自动恢复属于待办 01，实际平台恢复以演练记录为准。

**有没有真实收益或食品安全效果？** 当前没有可公开核验的门店效果数据；先展示工程拒动、回执和恢复证据，再以影子试点测量真实效果，不给出未经验证的节省比例。

## 9. 试点如何证明有用

### 9.1 指标必须有分母和测量边界

| 指标 | 建议定义 | 解释限制 |
|---|---|---|
| 无授权或证据不足放行 | 被系统允许的此类放行动作数，同时报告全部放行请求数 | 试点零次不证明永远安全；发生即停止相应自动化并排查 |
| 遏制确认时长 | 异常被确认到所有应覆盖渠道和实物保护确认的时长，报告中位数及高分位 | 只有命令发送时间不能代表完成停售 |
| 未覆盖量 | 应控制商品数量中尚未取得保护确认的数量及原因 | 批次未知时单列未知，不从分母排除 |
| 告警质量 | 按设备日统计误报；按独立标注事件统计检出与遗漏 | 未经标注的无告警时段不能自动算作正确；样本按设备/商品分层 |
| 人工负担 | 每事件实际处理分钟、交接次数、重复录入次数 | 不把模型运行时长当人工节省 |
| 经营影响 | 不必要停售时长、报损、误派工单、停机及系统运行成本 | 避免损失是反事实估算，需对照与不确定性，不能直接当营收 |
| 可追溯完整率 | 具备对象、策略、授权、执行、回查和关闭理由的事件数／全部事件数 | 有一条 Trace 不代表完整证据链 |
| 恢复成功与升级 | 在预算内恢复的任务、人工升级数、未处理队列年龄 | 不用“最终都重试成功”掩盖过长等待 |

### 9.2 公平评估方案

保留人工现行流程、规则＋工单基线和 Agent 辅助流程，比较相同类型事件。按门店和时段记录差异，防止只选轻微故障；评估人核对真实记录而非接受模型自报。安全门在各组保持一致，不能故意撤掉基线的审批权限制造多 Agent 优势。

优先验证：证据遗漏有没有减少、员工能否执行建议、哪些情况仍需人工、错误建议是否被门禁挡住、管理者能否查清未结原因。样本量与观察周期由事件频率和所需置信程度确定；本报告不编造试点规模或统计显著性。

## 10. 现场调研需要补的最小事实

这部分是调研清单，不是要求现在逐条答复。尚未联系任何门店、人员或供应商。

1. 最近几次冷柜异常的原始记录：谁发现、如何通知、谁处理、哪里最慢、最后怎么认定完成。
2. 商品品类、标签存储条件、实际批次标识方式，POS 能否识别批次，外卖订单如何拦截。
3. 冷柜探头位置、采样周期、除霜计划、网关离线行为，人工测温仪器与校准记录。
4. 店员接单、交班、夜间值守、代理审批和维修商响应方式；遇到“做不了”目前如何升级。
5. 备用冷柜容量、转移路径、数量核对、接收确认和报损凭证；是否有跨店转移或委托储存。
6. 已售商品、加工商品、召回和其他停售原因如何关联，谁有权决定后续处理。
7. 现有系统可提供的接口、权限、回调、幂等和对账能力，允许试点的动作范围与成本边界。
8. 数据保管、访问权限、员工影像和顾客交易信息的最小需求，以及可向评委展示的脱敏证据。
