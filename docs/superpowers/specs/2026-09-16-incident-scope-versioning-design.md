# T02：事件范围版本、审批绑定与拆批设计

状态：方向已于 2026-09-16 获用户确认；本详细设计待审阅，尚未实现。
基线：`b6773a2`。统一进度仍只维护在 `docs/待办.md`，本文不是另一份待办。

## 1. 已确认目标与范围

采用范围版本化：补货、移柜、拆批改变事件范围时触发必要遏制；旧审批不得覆盖新增或已变化对象；保留已完成动作及凭证，对变化部分重新审批、独立核验。拆批必须数量守恒并保留父子关系。

本设计完成 T02 的内部协议、状态和安全门，不把合成输入变为可信现场事实。真实 POS/WMS、跨店交接、实物来源与审批人接入仍单独验收，不因为内部模型完成而勾选全部 T02。

方案取舍：已选“范围版本与对象快照绑定”，而非全部变化永久转人工，也不采用重开事件、复制旧批准或清空历史的方式处理同一开放事件。无法确认变化来源或结果的输入仍转人工核对。

## 2. 当前代码依据

- `runtime.py:RuntimeService.open` 固定保存当时设备批次；`snapshot` 据此计算待遏制对象。
- `mcp/p0.py:create_approval` 保存动作类型、金额和处置方式，但没有结构化目标批次/数量绑定；`_require_approval` 不核对这样的对象快照。
- `domain/service.py:recompute` 和 `close_after_learning` 根据已记录批次计算终态；仅锁原批次不能保护新出现的对象。
- `RuntimeContextBus` 已有 CAS；`RuntimeService.call` 已有业务事务与门店作用域锁。应复用这些机制，不另建协调系统。
- `inventory_batches.quantity` 当前为整数。本次维持整数计量，不隐含引入重量、精度或单位换算。

## 3. 数据与不变量

事件增加 `scope_version`（初始 1）、当前范围快照及其规范化摘要。现有 `IncidentCase.version`、Context CAS version 和恢复 generation 各司其职，不能替代范围版本。

范围快照包括 tenant/store、关联设备、当前有效批次及每批 SKU、整数数量、位置和规则引用。按稳定键排序再生成摘要，不依赖 JSON 字段顺序。保留历史范围与变更来源，移出原设备不等于移出事件责任范围。

新增范围修订和批次谱系持久化记录：

- 修订：事件、前后版本/摘要、变更 ID、输入摘要、来源引用、操作者、时间及前后对象差异；同事件版本及来源变更 ID 唯一。
- 谱系：父批次、子批次、变更 ID、拆分前数量及分配数量，限制在同租户同门店；禁止循环和重复消费父批次。
- 批次增加生命周期标识（默认 active）；完整拆分后父批次 retired、可用数量归零，历史数量保留在谱系中。余额也必须是明确子批次，不丢弃余量。
- 审批、动作和复核绑定范围版本、结构化目标快照及摘要；审批记录保留原决定，适用性失效与“人工拒绝”区分。

所有合计使用整数；布尔值、负数、零数量子批、重复子 ID、跨 SKU/门店/租户、总量不等、父批次已终结或已拆分均拒绝。不能通过更新旧批次 ID 的含义来复用旧凭证。

## 4. 范围变更入口与事务

新增受控 runtime 范围修订入口：接收事件、预期范围版本、预期 Context 版本、稳定变更 ID、来源引用与结构化新增/同店位置变更/拆分请求。服务端从数据库生成规范快照，不信任客户端给出的“已批准”“已核验”或任意删除列表。

首版由已有同门店 Human 身份提交；Orchestrator 可发现并报告差异，但不能凭模型判断制造库存事实。场景引擎通过既有显式合成开关接入，并保留合成来源标记。无来源、未知库存差异进入待核对状态，禁止放行/关闭；不直接伪造变更事实或外部停售成功。

同一事务内完成：授权与参数校验 → 门店范围锁 → 所有关联开放事件及批次稳定顺序锁定 → CAS/幂等检查 → 数量/谱系校验 → 库存和范围修订 → 审批/租约适用性更新 → 遏制待办及审计 → 提交。SQLite 与 PG 保持等价约束，失败不能留下半次拆分或仅更新一处范围。

一个批次涉及多个开放事件时，变更必须一并更新这些事件并检查相应版本；不得仅处理调用者选中的一个事件。跨店流转不通过本同店入口直接改归属，须独立交接流程；未知去向保留责任和限制。

已关闭事件保持历史不可变；关闭之后的新暴露/补货创建有来源关联的新事件，不自动把过去成功的关闭改写成“从未发生”。关闭与范围修订同时发生时通过同一锁序串行化：先修订则旧关闭失败；先关闭则变化进入新事件路径。

## 5. 审批、幂等与已完成动作

申请审批必须明确动作目标快照，至少绑定批次/数量/位置、动作类型、金额或处置方式、规则版本。审批决定与执行时均重新核对目标，新增或数量/位置变化不在旧批准内。

全局范围扩展不自动否定未变化对象的原批准：仅在原 action_id、原目标摘要、原约束和有效期仍一致时继续使用，不能换 action_id、扩大对象或复制批准。变化对象未消费的批准标记为不再适用，并生成新的待审批动作；历史批准保持可追溯。

已成功动作及其回执只保留历史，不回滚现实副作用、不重发工单。相同幂等键和完全相同历史请求可返回明确标记的旧结果，但不能因此推进当前范围的 checkpoint；不同请求复用旧键拒绝。结果未知的在途动作先对账，不能借范围升级立即重做。

旧协议没有结构化目标绑定的未消费批准，在启用新协议时转为需重审；不能凭主观解释 subject 字符串补出授权。已有完成记录不被迁移伪造成当前范围授权。

## 6. 遏制、恢复、独立核验与关闭

修订后失效的是旧范围下的执行授权与推进资格，而非历史记录。旧 Worker 租约不能继续写；为本轮新增/变化且未证明已遏制的对象生成受控遏制任务。外部渠道尚未回执时状态必须是待确认，不能仅因任务已生成就写 CONTAINED。

复用现有恢复轮次：保留历史 checkpoint/输出，当前轮次重新计算需要执行的阶段与对象。未变化对象的已成功副作用不重做；变化对象必须完成自己的审批、动作和证据链。不要通过删除 checkpoint 或复用原动作 ID 假装重新执行。

Auditor 对当前完整范围汇总核验，但可以引用仍适用的未变化对象证据。新增/拆分子批次不能仅凭父批次旧凭证放行；需要明确覆盖子对象数量、当前动作与独立确认的新记录。设备未变化也仍需满足原有时效及健康门禁。

解除停售和关闭必须在同一有效范围版本上核对：库存来源对账、所有有效叶子批次数量、必要渠道回执、处置/实物证据、审批适用性与独立复核。任何范围缺口、陈旧复核、旧租约或未知执行结果均阻断。迁移或新字段不能绕过现有温度/证据/角色/RLS 安全门。

## 7. 迁移、接口与可观测性

SQLite/PG 增量迁移，不清库；旧事件能按历史原范围只读回放。开放旧事件在受控升级时建立初始快照；发现当前库存不一致则进入待核对，不能悄悄扩展历史授权。新服务在迁移缺失时 readiness 拒绝，不自动回落旧写入协议。

统一更新 runtime schema、Worker 包协议、MCP 审批参数、数据库约束和只读后台；详情展示当前/历史范围、差异、批准适用性、谱系与新一轮工作。旧客户端的缺版本写请求在切换新协议后明确拒绝，不能默认填当前版本。

迁移先备份并验证可恢复，切换时停止旧写入者；出现问题先暂停写入。已有范围修订数据时不直接回滚到不认识新协议的旧二进制。生产/托管迁移仍需目标环境授权。

## 8. 验收清单

1. 同范围重送不升版、不重复遏制；相同变更 ID 的不同内容拒绝。
2. 新增批次立即阻断旧范围放行；旧批准不能覆盖新对象，未变化对象的原动作不重复执行。
3. 移柜保留事件责任与限制；跨店或未知去向不能被同店入口消去。
4. 拆分整数数量守恒、完整父子关系、余额显式，拒绝重复/循环/跨域/终结父批；父凭证不能自动成为子批放行证据。
5. 变化与审批决定、执行、失响应重试、复核、解除停售、关闭并发；CAS/锁序防止旧范围副作用和重复动作。
6. 多个开放事件共用批次时全部原子更新；任何一个版本冲突则整个事务回滚。
7. 旧租约迟到、旧输出重放和恢复扫描器竞争不能推进新范围；未知副作用先对账。
8. 新范围完整复核通过才可关闭；不因设备正常或某个子批完成关闭整个事件。
9. SQLite 与真实独立受限 PG 登录分别执行正反例；含迁移旧数据、RLS、审计追加、失败回滚与进程重启恢复。
10. 完整回归、Worker 协议与制品、安装包/镜像、只读后台及历史回放兼容验收；真实 AT/Human/POS/托管 PG 另列，不与合成结果混算。

通过上述内部验收只能完成范围版本与拆批协议；不能宣称全部真实 T02、其他 F/T 项或总目标完成。
