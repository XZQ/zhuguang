# 逐光｜真实门店差距与演进路线

> 核对日期：2026-08-28（北京时间）。本文比较的是当前仓库与连锁便利店真实冷柜失温处置，不构成食品安全、HACCP、法律或监管意见。真实阈值和放行规则必须由企业食品安全负责人结合商品标签、设备说明书、企业 HACCP 计划和所在地适用法规批准。

## 1. 结论

“冷柜失温”仍然适合作为比赛唯一主展示场景，但当前项目只能定义为**可运行的事故协同与安全控制原型**，不能定义为生产食品安全系统。

这个判断并不等于把产品永久缩成一个功能：

- 产品定位仍是“连锁便利店多 Agent 异常闭环系统”；
- 冷柜失温是主叙事，用来完整展示发现、诊断、审批、执行、验证和复盘；
- 6 个 Scenario 是同一业务场景的 6 种现实分支，不是 6 个互不相关的主场景；
- 缺货和价签异常继续作为补充入口，用于证明框架可复用，不与主 Demo 争夺时间。

当前实现已经做对了三个关键抽象：先停售遏制、设备恢复不等于商品可放行、Executor 回执不等于 Auditor 独立验证。这些是生产演进的正确骨架。真实落地的主要差距不在于再增加 Agent，而在于**把合成事实、角色字符串和单机状态替换为可认证的人、设备、商品批次和企业系统记录**。

## 2. 第一性原理

真实门店要优化的不是“告警处理速度”一个指标，而是同时满足四个目标：

1. 不让可能不安全的商品继续销售；
2. 不因误报大面积停售、报损或浪费人工；
3. 尽快恢复设备和销售能力；
4. 对每个判断、动作和责任人都能追溯、复核和问责。

因此系统必须同时维护两条独立状态链：

```text
设备状态：正常 -> 异常 -> 检修 -> 恢复 -> 复验
商品状态：在售 -> 停售/隔离 -> 评估 -> 转移/放行/报损 -> 复核
```

设备温度恢复只能推进第一条链，不能自动结束第二条链。LLM/Agent 可以整理证据、提出假设和编排任务，但商品放行依据必须来自版本化规则、可靠测量和获授权人员；高风险动作不能由模型自由决定。

## 3. 当前仓库能证明什么

| 维度 | 当前事实 | 证据边界 |
|---|---|---|

## 5. 真实数据模型应补齐的最小字段

### 5.1 商品与策略

- `tenant_id`、`sku_id`、`lot_id`、商品类别、包装状态、保质期；
- 标签温度范围、企业 HACCP/食品安全计划引用、地区法规引用；
- 从收货、仓储到陈列的累计暴露片段，而不是只看当前柜温；
- 处置选项、所需证据、批准角色、版本、生效期和撤销原因。

### 5.2 设备与测量

- 冷柜、控制器、探头和网关的独立 ID、型号、安装位置和时钟质量；
- 精度、分辨率、校准日期、到期日、证书引用、漂移和维护历史；
- 柜内空气温度、模拟商品温度和实际商品中心温度的测量类型；
- 缺测、重复、乱序、离群、网关离线和人工复测的质量状态。

### 5.3 人员、审批和维修

- 员工/服务商真实身份、岗位、门店/区域权限、班次和委托链；
- 审批动作精确绑定的批次、处置、金额、证据版本和过期时间；
- 服务商接单、派工、到场、维修、复测和关闭回执；
- 所有状态变更的签名、来源系统、外部单号和不可变审计引用。

## 6. 建议生产架构

```text
IoT/网关 -> 数据质量与规则引擎 -> Incident 事件总线
                                   |
                                   v
                         AgentTeams 协同层
                    Sentry / Diagnoser / Executor / Auditor
                       |       |          |          |
                    只读证据  建议      受控动作     独立回查
                       |       |          |          |
                 POS / WMS / ERP / 审批 / CMMS / Evidence Store
                                   |
                                   v
                         人工值班台与移动端 SOP
```

生产实现应保留当前领域模型和 Adapter 分层，新增 `ProductionAdapter`，不要把企业 API 细节写进 Agent。外部写采用至少一次投递 + 幂等键 + 写后回查 + 定时对账；跨系统无法原子提交时，使用 Saga/补偿和明确的人工责任人，不宣称“严格 exactly-once”。

## 7. 灰度演进路线

### R0：比赛工程闭环（当前）

- 保持合成数据、确定性 Scenario 和明确免责声明；
- 补齐真实 AgentTeams Team Room、Worker 委派、MCP 返回和平台 Trace；
- 在可信网关或 MCP Adapter 完成动态 Worker 身份到 Actor 的映射，并验证匿名/错误 Token 拒绝、越权 `FORBIDDEN` 和正确主体审计；
- 录制正常分支与 partial/超时失败分支；
- 在隔离 PolarDB 实例完成双底座一致性、RLS/只读、pg_cron、月分区和 OSS 归档/恢复验收；
- 用真实复盘语料建立 RAG 标注集，只报告带样本量的 Recall@K/MRR，不提前写改善率；
- 不把本地 6/6 写成生产准确率，不把 ScenarioEngine 写成人工审批。

### R1：影子模式试点

- 选择少量门店和不同型号冷柜，仅读取真实 IoT、库存和人工测温；
- Agent 给出建议，但不自动写 POS/WMS/审批/工单；
- 并行记录人工原流程，建立故障真值、误报、漏报、响应时间和损失基线；
- 完成传感器盘点、校准、时钟同步和商品策略签批。

退出条件：真实数据覆盖率和质量达到企业约定门槛；每条建议可追溯到原始证据；食品安全负责人确认规则；未发生跨租户或越权访问。

### R2：受控遏制试点

- 仅开放预授权、可逆且可快速人工接管的动作，例如对明确批次发起停售；
- POS/WMS 双写必须回查，对账失败时保持更保守状态；
- 处置、放行和高金额维修继续人工批准；
- 接入真实审批排班和维修商接单/到场回执。

退出条件：未审批放行、错误关闭、不可追溯写入均为 0；所有 partial/超时都有明确 owner 和 SLA；完成回滚/补偿、断网和外部系统故障演练。

### R3：有限生产

- 扩展到多门店并发，启用多租户隔离、HA、备份恢复和在线 SLO；
- 对已验证故障类型开放自动编排，对新设备/新商品/新地区默认降级为人工；
- 按周复盘误报、漏报、停售损失、维修履约和规则漂移；
- 模型、Skill、策略和外部 API 每次升级均做冻结集回归和可回退发布。

### R4：规模化复制

- 通过设备/商品/地区模板复用，而不是复制统一温度阈值；
- 建立供应商、设备型号、故障码和处置效果的跨店知识候选；
- 知识必须经过审核、版本化和实际检索验证后，才能称为 RAG/知识飞轮；
- 形成食品安全、运维、门店运营和信息安全的联合治理机制。

## 8. 试点 KPI 与验收

### 8.1 安全红线

- 未授权商品放行数；
- 设备恢复导致的自动商品放行数；
- 无独立回查即关闭的事故数；
- 跨租户数据访问或动作数；
- 无审批、无审计或无法关联外部单号的高风险写入数。

以上指标在试点中应以 **0** 为门禁，不与效率指标加权抵消。

### 8.2 运营与质量指标

- 告警 precision/recall、每设备日误报数、数据缺失率和时钟偏移；
- 从异常发生到发现、停售、人工确认、维修接单、到场、恢复和放行的 P50/P95；
- 审批超时率、服务商拒单/改派率、外部系统写后回查一致率；
- 停售批次数、停售分钟、报损金额、避免损失估算、人工处理分钟和设备停机时间；
- 按设备型号、商品类别、门店和故障类型分层的结果，不只报告总平均值。

具体数值目标应先用 R1 基线和企业风险偏好确定。当前仓库的“最大 5 分钟”和 6/6 只属于合成验收，不直接转为生产 SLA。

## 9. 生产上线 Definition of Done

只有同时取得以下证据，才能把状态从“比赛原型”改成“生产可用”：

1. 企业食品安全/HACCP 负责人批准的商品策略、处置规则和例外流程；
2. 传感器台账、校准证书、人工测温 SOP 和抽检结果；
3. 真实 IAM、排班、委托、审批和维修商责任链；
4. POS/WMS/ERP/IoT/审批/CMMS 的集成测试、故障演练和对账报告；
5. 多租户隔离、鉴权、密钥轮换、审计防篡改和安全测试；
6. 并发、容量、备份恢复、RPO/RTO 和门店断网演练；
7. 真实试点的告警、响应、损失和人工成本基线，以及食品安全零红线事件证明；
8. 模型/Skill/策略版本回归、人工接管和回退演练。

## 10. 对比赛实施优先级的影响

真实差距很多，但复赛前不应仓促伪接企业系统或堆叠云产品。最有价值的顺序是：

1. 先取得真实 AgentTeams 动态协同及 Worker → MCP 身份绑定证据；
2. 确认“阿里云官方用云 Skills”口径；
3. 同步 72/70/2 测试口径、消融与指挥台证据、PolarDB 条件 skip 和当前证据边界到全部材料；
4. 用本文清楚回答“为什么选冷柜失温、现在离生产还有多远”；
5. 将真实集成、HACCP 签批、传感器校准和试点 KPI 作为下一阶段，而不是包装成已完成。

这比继续增加主场景更可信：一个主场景的正常、误报、人工超时、设备恢复但商品不安全和工具 partial 分支，已经足以展示多 Agent 协同深度；额外场景只能证明广度，不能替代真实运行证据。
