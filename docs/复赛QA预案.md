#### Q1: Agent 结果正确性 - formal verification vs 端到端测试

**问题**: 如何保证 Agent 输出结果的正确性？是否有 formal verification？

**回答要点**:

1. **我们采用的是工程化验证体系，而非 formal verification**

2. **五层验证机制**:
   - Layer 1: JSON Schema 结构校验
   - Layer 2: PolicyEngine 策略评估
   - Layer 3: 业务规则校验（事件边界、幂等性）
   - Layer 4: Auditor 交叉验证
   - Layer 5: 人工审批

3. **为什么不用 formal verification**:
   - 冷链场景规则明确（温度阈值、批次状态），工程验证更可靠
   - LLM 输出难以形式化证明
   - 可解释、可测试、可审计

4. **关键证据**:
   - 详见 `docs/Agent验证机制.md`
   - 全量发现 72 项测试：70 通过，2 条 PolarDB 条件集成测试跳过

#### Q2: StateStore 一致性 - 乐观锁够不够？

**问题**: 你们用乐观锁，分布式场景下够用吗？需要 Raft/Paxos 吗？

**回答要点**:

1. **当前方案**: SQLite WAL + 乐观锁
   - `BEGIN IMMEDIATE` 事务获取写锁
   - `busy_timeout=10000ms` 处理锁等待
   - 幂等键防止重复执行

2. **单节点够用**: 评测环境是单节点，WAL 模式完全满足需求

3. **分布式方案**: PolarDB PostgreSQL
   - 仓库已有 `PostgresStateStore` 和 SQL profile
   - 仍需 schema bootstrap、账号权限、RLS scope、迁移与回滚验证
   - 托管实例尚未联调，不能说成只改连接串或零改动

4. **为什么不用 Raft/Paxos**:
   - 实现复杂度高
   - 需要应用层改造
   - 托管数据库降低数据库运维成本，但 SLA 与一致性能力仍需按实例验收

5. **关键证据**:
   - 详见 `docs/分布式一致性方案.md`
   - `src/dianxun/state/store.py` 当前实现

#### Q3: MCP Server 部署与延迟

**问题**: MCP 服务如何部署？延迟多少？有超时重试吗？

**回答要点**:

1. **当前部署模式**：
   - 标准库 `ThreadingHTTPServer` 独立 HTTP 服务，默认仅监听回环地址
   - 同进程嵌入属于规划，不是当前默认模式

2. **性能指标**：
   - 尚无可复现 P99 基准，不能承诺 `<50ms` SLA
   - 查询/写入延迟目标需在固定机器、数据库和样本量下重新压测

3. **超时重试策略**：
   - 服务端已实现 1 MiB 请求体上限
   - 仓库尚未提供统一客户端重试/熔断器，由调用方负责超时和安全重放

4. **幂等性保证**:
   - 所有写操作支持 idempotency_key
   - 重试安全，不产生副作用

5. **关键证据**:
   - 详见 `docs/MCP延迟与可靠性.md`
   - `src/dianxun/mcp/server.py` 实现

#### Q4: RAG 策略

**问题**: 知识检索用的什么策略？embedding vs keyword vs hybrid？

**回答要点**:

1. **当前方案**：Embedding 相似度检索；本地默认确定性 Hash Embedding，也支持 OpenAI-compatible provider。
   当前仓库没有 BM25 混合检索或 reranker 实现。

2. **Hybrid 优势**:
   - BM25: 精确术语匹配、可解释
   - Embedding: 语义相似性理解
   - 两者结合：兼顾精度和语义

3. **Reranker（规划）**：
   - 可在有真实语料基线后评估
   - 当前没有选定模型、实现或延迟证据

4. **方案对比**:

   | 方案 | 精度 | 速度 | 适用场景 |
   |------|------|------|----------|
   | BM25 | 中 | 快 | 精确术语 |
   | Embedding | 高 | 中 | 语义相似 |
   | **Hybrid** | **高** | **中** | **通用场景** |
   | Reranker | 最高 | 慢 | 高精度需求 |

5. **知识库设计**:
   - 知识候选需人工审核
   - 脱敏检查确保隐私
   - 置信度评分过滤低质量知识

#### Q6: 异常处理类型 - 已发生 vs 预防

**问题**: 你们处理的异常是已经发生的，还是预防性的？

**回答要点**:

1. **当前**: **已发生异常的闭环处理**
   - 冷柜失温：温度已经超过阈值
   - 缺货：库存已经为零
   - 价签错误：价格已经不一致

2. **为什么不做预防**:
   - 预测需要更多数据和模型
   - 预防误报成本高
   - 当前场景更适合"发现-处理"闭环

3. **可扩展性**:
   - 系统架构支持扩展到预测
   - IoT 数据可用于趋势分析
   - 知识库沉淀历史模式

#### Q7: Sentry 获取数据 - 轮询 vs 订阅？

**问题**: Sentry 如何获取 IoT 数据？轮询还是订阅？

**回答要点**:

1. **当前**：仓库评测由确定性场景输入和本地 Mock 驱动，没有真实 IoT 平台轮询或订阅接入。

2. **轮询 vs 订阅对比**:

   | 方式 | 延迟 | 实现复杂度 | 资源消耗 |
   |------|------|------------|----------|
   | 轮询 | ~30s | 低 | 中 |
   | 订阅 | ~1s | 高 | 低 |

3. **接入决策**：
   - 需根据真实 IoT 平台能力、告警时效和断线补偿机制选择轮询/MQTT/WebSocket
   - 在没有生产数据前不承诺 30 秒轮询或 1 秒订阅延迟

4. **未来规划**:
   - WebSocket 实时订阅（已在架构设计中）
   - MQTT 协议支持（IoT 标准协议）

#### Q8: 追问 - 冷柜失温是已发生还是即将发生？

**问题**: 冷柜失温事件，是温度已经升高了，还是即将升高？

**回答要点**:

1. **明确答案**: **温度已经升高（已发生异常）**

2. **场景说明**:
   - 冷柜正常温度: 0-4°C
   - 触发阈值: >8°C 持续 N 分钟
   - 当前证据: 确定性场景数据模拟传感器温度已超标；真实 IoT 数据仍待接入

3. **我们的处理**:
   - Sentry 发现: 温度异常已发生
   - 即时遏制: 立即冻结相关批次
   - 诊断决策: 判断原因和影响范围
   - 处置执行: 批次处置 + 设备维修
   - 独立验证: Auditor 确认处置完成

4. **为什么强调"已发生"**:
   - 食品安全事件必须快速响应
   - 已发生异常比预测更紧迫
   - 闭环验证比预测更可靠

## 回答技巧

### 1. 结构化回答

```
1. 明确结论（1句话）
2. 核心机制（2-3句）
3. 关键证据（1-2个）
4. 开放问题（可引导讨论）
```

### 2. 证据导向

- 每个回答至少引用一个具体证据
- 证据可以是代码、文档、测试、数据
- 准备好展示关键代码片段

### 3. 自信但谦逊

- 自信: 展示我们的设计是深思熟虑的
- 谦逊: 承认当前方案的局限性
- 开放: 讨论未来可能的演进

### 4. 引导讨论

- 在回答最后抛出一个开放问题
- 引导评委关注我们的优势
- 避免陷入防御性讨论

## 常见陷阱

| 陷阱 | 表现 | 应对 |
|------|------|------|
| 技术堆砌 | 列举太多技术细节 | 聚焦核心回答，细节备查 |
| 防御性 | "我们不是这样做的" | 积极正面地解释设计选择 |
| 模糊回答 | "这个要看情况" | 给出明确立场和理由 |
| 过度承诺 | "我们可以做..." | 只讲当前已实现的 |
